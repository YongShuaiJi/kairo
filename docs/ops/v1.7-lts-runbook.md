# Kairo V1.7 LTS Operations Runbook

This is the **canonical V1.7 LTS operations runbook** (roadmap §11.4). It covers exactly the nine
V1.7 incident families and the commands, metrics, and decision boundaries an on-call operator needs.
M4-A (health/build-info, §11.1), M4-B (business metrics, §11.2) and M4-C (support bundles, §11.3) are
already shipped and accepted; this runbook references their real endpoints, commands, and meter names
without redefining them.

> **Hard rules.** Alerts and runbook steps may reference **only** the ten frozen meter names in
> [§ Frozen metrics contract](#frozen-metrics-contract) and **only** their documented finite label
> values. Never invent a metric or label. To locate a *specific* object (rule, agent, instance, class,
> operation), use the **structured APIs, status endpoints, and support bundles** described below — never
> an unbounded label. Never paste real Token/password values; use shell variables (`$KAIRO_TOKEN`,
> `$KAIRO_AGENT_TOKEN`, …). Avoid commands that echo a secret (no `echo $KAIRO_TOKEN`).

## Marked command blocks

Every executable command block in this runbook is one of two kinds, marked with HTML-comment markers so
they do not change the rendered document:

- **`AUTOMATED-SAFE`** — repository-local, non-mutating, no-network commands that `scripts/v1.7/verify-runbooks.sh`
  parses and **executes from the repository root** in CI. Each has a unique stable `id`. The approved safe
  grammar is: `bash -n`, `python3 -m json.tool`, focused `mvn` tests, `git diff --check`, and read-only
  local file checks. The verifier rejects `rm`, `mv`, git *write* operations, `curl`, `docker stop/restart/down`,
  database mutation, `kill`, `shutdown`, `reset`, `disable`, `enable`, `sudo`, `eval`, command substitution,
  and shell redirection to repository files.
- **`OPERATOR-CONFIRMED`** — commands a human operator runs against a real environment (read-only network
  diagnosis **or** state-mutating recovery). `verify-runbooks.sh` validates that these markers are
  well-formed and carry unique IDs, but **never executes them**. They require a running Platform/Agent and
  may be state-mutating; confirm each before running.

Commands with no marker are illustrative snippets and are not executed or validated by the verifier.

## Shared foundations

### Endpoints and authentication

| Surface | URL (variable) | Auth | Notes |
| --- | --- | --- | --- |
| Platform health (aggregate) | `$KAIRO_PLATFORM_URL/actuator/health` | **none** | `show-details=always`; the only unauthenticated actuator surface |
| Liveness | `$KAIRO_PLATFORM_URL/actuator/health/liveness` | **none** | Process-liveness only (`livenessState`). DB/Redis/Agent offline can never drive it DOWN. |
| Readiness | `$KAIRO_PLATFORM_URL/actuator/health/readiness` | **none** | `readinessState, db, flyway, redis` (Redis self-gates on `kairo.platform.fencing.redis-enabled`). |
| Build info | `$KAIRO_PLATFORM_URL/actuator/info` | Bearer `$KAIRO_TOKEN` | Bounded `build`: `version`, `commit`, `time`, `javaTarget`, `contractBaseline`. |
| Metrics | `$KAIRO_PLATFORM_URL/actuator/metrics` | Bearer `$KAIRO_TOKEN` | Exposes the ten `kairo_*` meters. |
| Agent status (ops) | `kairo-ops status --url "$KAIRO_AGENT_URL"` | `--token "$KAIRO_AGENT_TOKEN"` (`X-Agent-Token`) | Local agent loopback, default `http://127.0.0.1:18080`. Works while Platform is down. |
| Agent support bundle | `kairo-ops support-bundle --output <zip>` | optional `--token` | Read-only, bounded (≤20 MiB, 30 s). |
| Platform support bundle | `kairo-cli diagnose --output <zip>` | `--token "$KAIRO_TOKEN"` | Read-only, bounded (≤20 MiB, 30 s). |

The two CLI jars are `kairo-cli/target/kairo-cli.jar` and `kairo-ops/target/kairo-ops.jar`. In production
these are the installed CLI binaries; the jar paths are the development form.

### kairo-ops emergency command set (local agent loopback)

`kairo-ops` talks **directly to the Agent**, not the Platform. This is the emergency path when the
Platform is unavailable. Every command except `status` and `support-bundle` is a **mutation** that
requires `--reason` and `--event` (an incident/event id) and is appended to the local audit log.

| Command | Method + path | Body | Audited |
| --- | --- | --- | --- |
| `status` | `GET /v1/status` | — | yes |
| `disable-rule --rule-id` | `POST /v1/rules/{rule-id}/disable` | `{reason,eventId}` | yes |
| `disable-all` | `POST /v1/agent/disable-all` | `{reason,eventId}` | yes |
| `enable-all` | `POST /v1/agent/enable-all` | `{reason,eventId}` | yes |
| `remove-rule --rule-id` | `DELETE /v1/rules/{rule-id}` | `{reason,eventId}` | yes |
| `reset-class --class-id` | `POST /v1/agent/reset-class` | `{classId,reason,eventId}` | yes |
| `reset-all` | `POST /v1/agent/reset-all` | `{reason,eventId}` | yes |
| `shutdown-agent` | `POST /v1/agent/shutdown` | `{reason,eventId}` | yes |
| `support-bundle --output` | (local collection) | — | **no** (read-only) |

The audit log is `~/.kairo/ops-audit.jsonl`; redirect it with the `KAIRO_OPS_AUDIT_PATH` environment
variable or the `kairo.ops.audit.path` system property (one JSONL line per audited command:
`timestamp`, `command`, `eventId`, `reason`, `status`, `response`). The audit line never carries the
raw token.

### Frozen metrics contract

The V1.7 operational metric contract (M4-B, §11.2). Alert on these names and these finite labels only.
The full machine-readable mirror is [`v1.7-finite-labels.json`](./v1.7-finite-labels.json) (the Java
`KairoMetricsCatalog` is authoritative).

| Meter | Type | Tags (finite values) |
| --- | --- | --- |
| `kairo_agent_online` | gauge | `status`: ACTIVE, ONLINE, STOPPING, DISABLED, OFFLINE, OTHER |
| `kairo_agent_command_backlog` | gauge | `status`: PENDING, DISPATCHED, ACKED, FAILED, OTHER · `command_type`: V1 set + OTHER |
| `kairo_agent_command_total` | counter | `command_type`: V1 set + OTHER · `result`: SUCCESS, FAILURE, TIMEOUT, OTHER |
| `kairo_operation_total` | counter | `operation_type`: OperationType + OTHER · `result`: SUCCESS, FAILURE, CANCELLED, TIMEOUT, OTHER |
| `kairo_operation_duration_seconds` | timer | `operation_type` · `result` (same vocab as above) |
| `kairo_runtime_rule_targets` | gauge | `state`: FRESH, DRIFTED, UNRESOLVED, OTHER |
| `kairo_reconcile_total` | counter | `result`: SUCCESS, FAILURE, OTHER |
| `kairo_rollback_total` | counter | `result`: SUCCESS, FAILURE, OTHER |
| `kairo_ttl_cleanup_total` | counter | `result`: SUCCESS, FAILURE, OTHER |
| `kairo_platform_build_info` | gauge=1 | `version` · `commit` |

`kairo_agent_command_backlog` includes recently-terminal commands (ACKED/FAILED) before cleanup; treat
true backlog as `status` ∈ {PENDING, DISPATCHED}. Unknown DB values collapse to OTHER, never dropped.

## Family 1 — Platform startup / Flyway failure

**Observable signal.** The Platform process exits during bootstrap, or `/actuator/health/readiness`
reports DOWN with the `flyway` component describing invalid migrations (≤5 `invalidMigrations`
listed). Startup logs show a Flyway `ValidateException` or migration failure.

**Metrics (finite labels).** No counter increments (the application context never reached the dispatch
path). Confirm the deployed build with `kairo_platform_build_info` (`version`, `commit`) and the
`/actuator/info` `contractBaseline`. Do not alert on a startup-only failure with a backlog metric —
there is no backlog until the scheduler is up.

**Read-only diagnosis.**

<!-- OPERATOR-CONFIRMED id="op-readiness-flyway" -->
```bash
curl -fsS "$KAIRO_PLATFORM_URL/actuator/health/readiness" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

The `flyway` component detail names the offending migration(s) without credentials or stack traces.
For a bounded offline snapshot when the Platform is still bootstrapping/unhealthy, use the Agent-side
bundle (it does not depend on the Platform):

<!-- OPERATOR-CONFIRMED id="op-agent-bundle-startup" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar support-bundle \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --output "$KAIRO_BUNDLE_DIR/agent-startup.zip"
```
<!-- /OPERATOR-CONFIRMED -->

**Decision boundary.** If readiness is DOWN *only* on `flyway` and the DB is reachable, the cause is a
migration defect or a stale migration checksum — a **code/migration** problem, not an infra outage. If
`db` is also DOWN, treat as [Family 2](#family-2--postgresqlredis-unavailable).

**Safe recovery.** This is a code/migration change requiring a redeploy, not an in-place mutation. Do
**not** attempt Flyway `repair`/`clean` against production from this runbook — that is a schema mutation
outside the M4-D safe boundary. Roll the Platform back to the last known-good build (see
[Family 9](#family-9--v16--v17-upgrade-and-rollback-protection)).

**Abort / escalation.** Abort and escalate to the release owner if: the failing migration is not in the
release notes; `db` is also DOWN; or the `contractBaseline` in `/actuator/info` does not match the
expected V1.7 baseline. Do not proceed with `flyway repair` without a reviewed change.

**Recovery verification.**

<!-- OPERATOR-CONFIRMED id="op-readiness-verify-startup" -->
```bash
curl -fsS "$KAIRO_PLATFORM_URL/actuator/health" | jq '{status, components:{flyway:{status},db:{status}}}'
```
<!-- /OPERATOR-CONFIRMED -->

Expect overall `status=UP` with `flyway` and `db` components UP after a clean redeploy.

## Family 2 — PostgreSQL / Redis unavailable

**Observable signal.** `/actuator/health/readiness` is DOWN on `db` (PostgreSQL) and/or `redis` (only
when `kairo.platform.fencing.redis-enabled=true`). **Liveness stays UP** — the process is alive; this is
a dependency outage, not a process failure. PostgreSQL is the authoritative state store; Redis is only
the fencing-token sequence coordinator.

**Metrics (finite labels).** `kairo_operation_total{result=FAILURE}` and
`kairo_reconcile_total{result=FAILURE}` rise as writes/reconciliation fail against the DB;
`kairo_agent_command_total{result=FAILURE}` may rise if dispatch cannot persist. Confirm the build with
`kairo_platform_build_info`. These are *symptoms* of the dependency outage — the root signal is the
readiness component, not a metric.

**Read-only diagnosis.**

<!-- OPERATOR-CONFIRMED id="op-readiness-deps" -->
```bash
curl -fsS "$KAIRO_PLATFORM_URL/actuator/health/readiness" | jq '.components | {db,redis}'
```
<!-- /OPERATOR-CONFIRMED -->

The `db` DOWN `error` is the connection exception message only (no JDBC URL, no credentials, no stack).
`redis` reports UP/disabled when fencing-Redis is off; it is DOWN only when configured-and-required.

**Decision boundary.** This is an **external infrastructure** action: restore PostgreSQL/Redis at the
infrastructure layer. The Platform cannot self-heal a missing database. If only Redis is down and
fencing-Redis is optional, the Platform remains ready (Redis is not in the readiness group unless
configured required).

**Safe recovery.** Restore the PostgreSQL primary (and Redis if configured). Do **not** restart the
Platform to mask the outage — let it reconnect. The Lettuce Redis client and the JDBC pool reconnect
automatically once the dependency returns.

**Abort / escalation.** Escalate to the DBA/infra owner. If PostgreSQL cannot be restored promptly,
consider `shutdown-agent` per [Family 8](#family-8--emergency-recovery-with-kairo-ops-while-platform-is-unavailable)
to stop agents from acting on stale Platform state. Abort if `db` DOWN persists after the infra team
confirms PostgreSQL is healthy — that indicates a Platform-side connection/config defect, not infra.

**Recovery verification.** Readiness returns to UP and the failure counters stop rising:

<!-- OPERATOR-CONFIRMED id="op-readiness-verify-deps" -->
```bash
curl -fsS "$KAIRO_PLATFORM_URL/actuator/health/readiness" | jq '{status,components:{db:{status},redis:{status}}}'
```
<!-- /OPERATOR-CONFIRMED -->

Confirm `kairo_operation_total{result=FAILURE}` and `kairo_reconcile_total{result=FAILURE}` stop
increasing on the next scrape (`/actuator/metrics/kairo_operation_total` and `/kairo_reconcile_total`).
A failure total is cumulative — verify the *rate* has fallen to zero, not that the total is zero.

## Family 3 — Agent offline or command backlog

**Observable signal.** `kairo_agent_online{status=OFFLINE}` or `{status=DISABLED}` for an agent.
`kairo_agent_command_backlog{status=PENDING}` and/or `{status=DISPATCHED}` rising (filter backlog to
`status` ∈ {PENDING, DISPATCHED}; ACKED/FAILED are pre-cleanup terminal). `kairo_agent_command_total{result=TIMEOUT}`
rising means commands are exhausting retries without ack.

**Metrics (finite labels).** `kairo_agent_online` (status), `kairo_agent_command_backlog` (status,
command_type), `kairo_agent_command_total` (command_type, result). To find *which* agent/rule, use the
structured resource queries below — never an `agentId`/`ruleId` label.

**Read-only diagnosis.** List the per-agent command backlog and online state from metrics, then locate
the specific agent via the structured status API:

<!-- OPERATOR-CONFIRMED id="op-metrics-agent" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" \
  "$KAIRO_PLATFORM_URL/actuator/metrics/kairo_agent_command_backlog?tag=status=PENDING" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

<!-- OPERATOR-CONFIRMED id="op-ops-status" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar status --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

`kairo-ops status` returns the Agent's existing status response. Treat that direct response as
operator-sensitive and do not archive it as a support artifact. The `support-bundle` command below
applies the bounded `jvm`/`metrics` projection and redaction rules before writing an archive:

<!-- OPERATOR-CONFIRMED id="op-agent-bundle-backlog" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar support-bundle \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --output "$KAIRO_BUNDLE_DIR/agent-backlog.zip"
```
<!-- /OPERATOR-CONFIRMED -->

**Decision boundary.** If the agent process is gone (`status=OFFLINE`) → infrastructure/process action,
restart the agent. If the agent is up but backlog grows and commands `TIMEOUT` → the agent is not
acking; reconcile (M1-D) or check the target JVM. If only one `command_type` is stuck, locate that
operation via `kairo-cli operations` (structured) — not a metric label.

**Safe recovery.** Operator-confirmed: run reconciliation (the scheduler reconciles desired vs actual
and re-dispatches/degrades). If the agent must be stopped to stop the backlog, use `disable-all` then
verify via `status` (see [Family 8](#family-8--emergency-recovery-with-kairo-ops-while-platform-is-unavailable)
for the documented disable→verify→enable loop). Do not `reset-all` unless you intend to drop all
enhancements on that agent.

**Abort / escalation.** Escalate if `kairo_agent_command_total{result=TIMEOUT}` keeps rising after
reconciliation and the agent `status` shows ONLINE — that indicates a target-JVM or agent-internal
defect, not a dispatch backlog. Abort any `disable-all` if it would break a live-critical target.

**Recovery verification.** `kairo_agent_online{status=ONLINE}`, `kairo_agent_command_backlog{status=PENDING}`
returning toward zero, and `kairo_agent_command_total{result=TIMEOUT}` rate at zero:

<!-- OPERATOR-CONFIRMED id="op-metrics-agent-verify" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" \
  "$KAIRO_PLATFORM_URL/actuator/metrics/kairo_agent_command_backlog?tag=status=PENDING" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

## Family 4 — Rollout stuck, partial failure, and state drift

**Observable signal.** An operation does not reach a terminal state: `kairo_operation_total{result=FAILURE}`
or `{result=TIMEOUT}` rising, or `kairo_operation_duration_seconds` p99 climbing. `kairo_runtime_rule_targets{state=DRIFTED}`
or `{state=UNRESOLVED}` indicates a target's runtime state has diverged from the defined rule version.
`kairo_reconcile_total{result=FAILURE}` may rise if reconciliation cannot resolve the drift.

**Metrics (finite labels).** `kairo_operation_total` (operation_type, result),
`kairo_operation_duration_seconds` (operation_type, result), `kairo_runtime_rule_targets` (state),
`kairo_reconcile_total` (result). Locate the specific operation/rule via the structured operation API,
not a label.

**Read-only diagnosis.** Inspect the operation and the drift status via the structured APIs:

<!-- OPERATOR-CONFIRMED id="op-operations-list" -->
```bash
java -jar kairo-cli/target/kairo-cli.jar operations --status RUNNING --limit 20 \
  --base-url "$KAIRO_PLATFORM_URL" --token "$KAIRO_TOKEN" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

<!-- OPERATOR-CONFIRMED id="op-operation-observe" -->
```bash
java -jar kairo-cli/target/kairo-cli.jar observe --operation "$OP_ID" \
  --base-url "$KAIRO_PLATFORM_URL" --token "$KAIRO_TOKEN" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

The direct `observe` response is an authenticated operational resource, not a redacted support
artifact. The Platform support bundle projects recent operations to `type`, `status`, `riskLevel`,
`progress`, timestamps, and a bounded `errorSummary.category`; it omits IDs, raw result/error
messages, script bodies, and stacks:

<!-- OPERATOR-CONFIRMED id="op-diagnose-rollout" -->
```bash
java -jar kairo-cli/target/kairo-cli.jar diagnose \
  --base-url "$KAIRO_PLATFORM_URL" --token "$KAIRO_TOKEN" \
  --output "$KAIRO_BUNDLE_DIR/platform-rollout.zip"
```
<!-- /OPERATOR-CONFIRMED -->

**Decision boundary.** A `DRIFTED` target is **not** auto-resolved — reconciling degrades it
(`DEGRADED` upsert) but does not silently re-enhance. If the operation is genuinely stuck
(non-terminal, no progress), the safe action is a **precise rollback** (unload the specific rule
version), not `reset-all`.

**Safe recovery.** Operator-confirmed precise rollback via the operation revert path, or `disable-rule`
for the single offending rule:

<!-- OPERATOR-CONFIRMED id="op-disable-rule" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar disable-rule \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --rule-id "$RULE_ID" --reason "$REASON" --event "$EVENT_ID" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

After the mutation, the audit log records `command`, `eventId`, `reason`, `status`, `response`.

**Abort / escalation.** Abort if the drifted target is load-bearing and `disable-rule`/rollback would
change live behaviour without approval. Escalate to the rule owner. If `kairo_runtime_rule_targets{state=UNRESOLVED}`
persists after reconcile, the target cannot be resolved (enhancement-location failure) — escalate rather
than force-reset.

**Recovery verification.** The operation reaches a terminal state and the target returns to `FRESH`:

<!-- OPERATOR-CONFIRMED id="op-metrics-drift-verify" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" \
  "$KAIRO_PLATFORM_URL/actuator/metrics/kairo_runtime_rule_targets?tag=state=DRIFTED" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

Confirm `kairo_operation_total{result=SUCCESS}` (or terminal FAILURE) for the operation and
`kairo_rollback_total{result=SUCCESS}` if a rollback ran.

## Family 5 — Unload failure and offline pending compensation

**Observable signal.** A precise unload (rollback) failed: `kairo_rollback_total{result=FAILURE}` rises.
If the agent was offline when the unload was scheduled, the compensation is **pending** until the agent
returns online (M1-E: offline-unload compensation; removed false-success fabrications — a pending unload
is never reported as succeeded). `kairo_runtime_rule_targets{state=DRIFTED}` may remain while pending.

**Metrics (finite labels).** `kairo_rollback_total` (result), `kairo_runtime_rule_targets` (state).
Pending compensations are located via the structured operation/registration state, not a label.

**Read-only diagnosis.** Confirm the agent is offline and the unload is pending:

<!-- OPERATOR-CONFIRMED id="op-ops-status-unload" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar status --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" | jq '{jvm:{status},metrics:{activeRuleCount,globallyEnabled}}'
```
<!-- /OPERATOR-CONFIRMED -->

<!-- OPERATOR-CONFIRMED id="op-metrics-rollback" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" \
  "$KAIRO_PLATFORM_URL/actuator/metrics/kairo_rollback_total?tag=result=FAILURE" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

**Decision boundary.** If the agent is offline, the unload **cannot** complete — do not treat the pending
state as a failure to retry blindly; `compensatePendingUnloads` runs first in `reconcileAgent` once the
agent is back. If the agent is online and the unload still fails, the enhancement cannot be precisely
reverted — fall back to `reset-class`.

**Safe recovery.** Bring the agent online (infra/process), then let reconciliation compensate the pending
unload. If online and precise unload keeps failing, reset the specific class:

<!-- OPERATOR-CONFIRMED id="op-reset-class" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar reset-class \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --class-id "$CLASS_ID" --reason "$REASON" --event "$EVENT_ID" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

`reset-class` is **precise** (one class); prefer it over `reset-all`. Verify via `status` afterwards.

**Abort / escalation.** Escalate if the agent cannot be brought online within the compensation window,
or if `reset-class` fails (the classId is malformed or the class is not enhanced). Do **not** `reset-all`
to clear a single failed unload — that drops every enhancement on the agent.

**Recovery verification.** After the agent is online and reconciliation runs, confirm the rollback
succeeded and the target is no longer drifted:

<!-- OPERATOR-CONFIRMED id="op-metrics-unload-verify" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" \
  "$KAIRO_PLATFORM_URL/actuator/metrics/kairo_rollback_total?tag=result=SUCCESS" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

`kairo_reconcile_total{result=SUCCESS}` should increment for the reconciled agent, and
`kairo_runtime_rule_targets{state=DRIFTED}` for the target should return to `FRESH` once compensated.
`OTHER` means an unknown/unrecognised persisted state and is an escalation signal, not recovery.

## Family 6 — TTL cleanup failure

**Observable signal.** `kairo_ttl_cleanup_total{result=FAILURE}` is rising. This counter is emitted by
the script-session expiry sweep: non-terminal script sessions may not be reaching `EXPIRED`, and
their best-effort revert may not be enqueued.

**Metrics (finite labels).** `kairo_ttl_cleanup_total` (result). There is no per-session metric and this
counter does not prove that generic terminal agent commands are being deleted. Locate the affected
script session via authenticated structured session/operation queries, not a label.

**Read-only diagnosis.**

<!-- OPERATOR-CONFIRMED id="op-metrics-ttl" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" \
  "$KAIRO_PLATFORM_URL/actuator/metrics/kairo_ttl_cleanup_total?tag=result=FAILURE" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

Collect a Platform bundle to capture recent operations and health without raw session/script bodies:

<!-- OPERATOR-CONFIRMED id="op-diagnose-ttl" -->
```bash
java -jar kairo-cli/target/kairo-cli.jar diagnose \
  --base-url "$KAIRO_PLATFORM_URL" --token "$KAIRO_TOKEN" \
  --output "$KAIRO_BUNDLE_DIR/platform-ttl.zip"
```
<!-- /OPERATOR-CONFIRMED -->

**Decision boundary.** A TTL cleanup failure is a Platform-side scheduler defect or a DB issue — not an
agent issue. Do not mutate agent state to fix a TTL problem. If `kairo_reconcile_total{result=FAILURE}`
is also rising, the DB may be the cause (cross-check [Family 2](#family-2--postgresqlredis-unavailable)).

**Safe recovery.** This is a Platform-side issue; the safe action is to let the scheduled cleanup retry
(it runs on a fixed schedule) after the underlying cause is resolved. If the scheduler is wedged, a
Platform restart is the recovery — coordinate as a deployment action, not an in-place mutation from
this runbook.

**Abort / escalation.** Escalate to the Platform owner. Abort if the failure correlates with a DB
outage (resolve that first). Do not run ad-hoc DELETE/UPDATE against `agent_command`/`script_session`
tables — that bypasses the idempotency/lease/lifecycle guards.

**Recovery verification.** `kairo_ttl_cleanup_total{result=SUCCESS}` increments on the next cycle;
then verify the affected non-terminal script sessions transitioned to `EXPIRED` and the intended
best-effort revert was enqueued:

<!-- OPERATOR-CONFIRMED id="op-metrics-ttl-verify" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" \
```

## Family 7 — Sustained heap / Metaspace / ClassLoader growth

**Observable signal.** There is **no** `kairo_*` heap/Metaspace/ClassLoader meter (the frozen contract
deliberately omits JVM-memory business metrics). Detect sustained growth with standard JVM telemetry
or owner-approved JVM tooling, then reproduce it with the M2-C leak check and M2-D soak harnesses.
The Agent support bundle exposes only Kairo activity counters (`loadedClassCount`, enhancement/rule
counts); these are correlation clues, not heap, Metaspace, or live-ClassLoader measurements. Confirm
the build with `kairo_platform_build_info`.

**Metrics (finite labels).** `kairo_platform_build_info` (`version`, `commit`) pins the build under
suspicion. The growth signal comes from standard JVM telemetry/tooling and the harnesses — never from
an invented `kairo_heap_*` meter or by treating `loadedClassCount` as proof of a memory leak.

**Read-only diagnosis.** Run the leak-check harness (it surfaces real ClassLoader pinning, e.g. Groovy
invoke pinning loaders) and collect an Agent bundle:

<!-- OPERATOR-CONFIRMED id="op-leak-check" -->
```bash
./scripts/v1.7/run-leak-check.sh --cycles 500 --output target/v1.7
```
<!-- /OPERATOR-CONFIRMED -->

<!-- OPERATOR-CONFIRMED id="op-agent-bundle-leak" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar support-bundle \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --output "$KAIRO_BUNDLE_DIR/agent-leak.zip"
```
<!-- /OPERATOR-CONFIRMED -->

Use `agent-status.json` → `metrics` only to correlate Kairo activity with the external JVM signal;
inspect `agent-events.json` for the bounded event log (≤100, projected to `timestamp`/`type` only).

**Decision boundary.** If the leak is reproducible in the leak-check/soak harness on a clean checkout,
it is a **product defect** (report it — do not mask it). If it appears only on one target, suspect the
specific rule/enhancement on that target and recover with a precise `reset-class`.

**Safe recovery.** Operator-confirmed precise unload of the suspected enhancement:

<!-- OPERATOR-CONFIRMED id="op-reset-class-leak" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar reset-class \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --class-id "$CLASS_ID" --reason "leak mitigation" --event "$EVENT_ID" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

If precise unload does not relieve the growth (the ClassLoader is pinned), the only safe recovery is to
restart the target JVM after unloading — coordinate as an application action.

**Abort / escalation.** Escalate to the Platform/agent owner. Do not take a full heap dump into a
support bundle (the bundle deliberately excludes full heap dumps and raw class bytes — collect those
out-of-band via the JVM tooling if the owner requests). Abort `reset-class` if the classId is not known
to be enhanced.

**Recovery verification.** After `reset-class` (or restart), confirm the heap/Metaspace/ClassLoader
signal stabilises in the same JVM telemetry/tooling that detected it. Use a fresh `kairo-ops status`
only to confirm the enhancement/rule counters, then re-run the leak-check harness on a clean tree:

<!-- OPERATOR-CONFIRMED id="op-ops-status-leak-verify" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar status --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  | jq '.metrics | {loadedClassCount,enhancedClassCount,activeRuleCount}'
```
<!-- /OPERATOR-CONFIRMED -->

## Family 8 — Emergency recovery with kairo-ops while Platform is unavailable

**Observable signal.** The Platform is unreachable: `curl "$KAIRO_PLATFORM_URL/actuator/health"` fails
or times out. Agents are still running and their local loopback (`kairo-ops status`) responds. This is
the family exercised by the controlled drill (`scripts/v1.7/run-ops-drill.sh`) against an in-process
loopback stub — never a real Agent or external infrastructure.

**Metrics (finite labels).** None from the Platform (its `/actuator/metrics` is down). Use `kairo-ops
status` → `metrics` (RuntimeMetrics) and the audit log for the local signal. `kairo_platform_build_info`
is unavailable while the Platform is down — confirm the build from the release manifest once restored.

**Read-only diagnosis.** Confirm the Platform is down and the Agent loopback is up:

<!-- OPERATOR-CONFIRMED id="op-platform-down-check" -->
```bash
curl -fsS --max-time 5 "$KAIRO_PLATFORM_URL/actuator/health" || echo "platform unreachable"
java -jar kairo-ops/target/kairo-ops.jar status --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" | jq '{jvm:{status},metrics:{globallyEnabled,activeRuleCount}}'
```
<!-- /OPERATOR-CONFIRMED -->

**Decision boundary.** `kairo-ops` talks directly to the Agent, so it works while the Platform is down.
Use it to **stop the agent acting on stale Platform state** until the Platform is restored. This is an
explicit operator-confirmed mutation — every command is audited with `--reason`/`--event`.

**Safe recovery.** Emergency disable, then **verify via status** (the documented disable→verify loop),
then restore once the Platform is back:

<!-- OPERATOR-CONFIRMED id="op-emergency-disable-all" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar disable-all \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --reason "platform unavailable" --event "$EVENT_ID" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

<!-- OPERATOR-CONFIRMED id="op-emergency-verify-disabled" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar status --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  | jq '{jvm:{status},metrics:{globallyEnabled}}'
```
<!-- /OPERATOR-CONFIRMED -->

Expect `globallyEnabled=false` and `jvm.status=DISABLED`. Once the Platform is restored, re-enable and
verify recovery:

<!-- OPERATOR-CONFIRMED id="op-emergency-enable-all" -->
```bash
java -jar kairo-ops/target/kairo-ops.jar enable-all \
  --url "$KAIRO_AGENT_URL" --token "$KAIRO_AGENT_TOKEN" \
  --reason "platform recovered" --event "$EVENT_ID" | jq .
```
<!-- /OPERATOR-CONFIRMED -->

For a single offending rule, prefer `disable-rule`; for a single drifted class, prefer `reset-class`;
reserve `shutdown-agent` for when the agent process itself must stop. Each is audited locally.

**Abort / escalation.** Abort if the Agent loopback is *also* unreachable — there is no `kairo-ops` path
and you must restart the agent process at the infrastructure layer. Escalate the Platform outage
separately ([Family 1](#family-1--platform-startup--flyway-failure)/[Family 2](#family-2--postgresqlredis-unavailable)).
Do not leave the agent in `DISABLED`/`shutdown` after the Platform recovers without re-enabling.

**Recovery verification.** After re-enable, `status` shows `globallyEnabled=true` and `jvm.status=ONLINE`,
and the Platform `/actuator/health` is UP. The audit log (`KAIRO_OPS_AUDIT_PATH`) contains one line per
emergency command with matching `eventId`/`reason`/`status=200`.

> The controlled drill proves this exact command path, the `X-Agent-Token` header, the fixed
> `{reason,eventId}`/`{classId,reason,eventId}` body, the audit line, and the disable→verify→enable
> recovery loop against an in-process loopback stub. It does **not** perform a real emergency mutation
> or contact a real Agent.

## Family 9 — V1.6 → V1.7 upgrade and application rollback protection

**Observable signal.** `/actuator/info` `build.version`/`commit` and `contractBaseline` (the V1.6.0
source baseline) identify the running build. `kairo_platform_build_info` carries the same identity.
After upgrade, readiness must be UP; a `SchemaCompatibilityGuard` failure (M1-F) or a Flyway migration
failure ([Family 1](#family-1--platform-startup--flyway-failure)) blocks a healthy upgrade.

**Metrics (finite labels).** `kairo_platform_build_info` (`version`, `commit`) to confirm the deployed
build before and after. No counter is specific to upgrade; use readiness + the schema guard.

**Read-only diagnosis.** Confirm the build identity and readiness on the new version:

<!-- OPERATOR-CONFIRMED id="op-info-upgrade" -->
```bash
curl -fsS -H "Authorization: Bearer $KAIRO_TOKEN" "$KAIRO_PLATFORM_URL/actuator/info" | jq .build
curl -fsS "$KAIRO_PLATFORM_URL/actuator/health/readiness" | jq '{status,components:{db:{status},flyway:{status}}}'
```
<!-- /OPERATOR-CONFIRMED -->

**Decision boundary.** V1.7 ships forward-only Flyway migrations; **there is no automated data
downgrade**. Rollback protection means: roll back the *application* to the prior build, which must
remain compatible with the migrated schema (the schema-compatibility guard enforces this). If a
migration is not backward-compatible with the prior build, do **not** roll back the application —
fix forward.

**Safe recovery.** Application rollback (redeploy the prior V1.7 or V1.6 build) is a deployment action,
not an in-place mutation from this runbook. Before rollback, drain in-flight operations: do not start
new rollouts; let `kairo_operation_total` terminal counts settle. Use `kairo-cli operations` to confirm
no non-terminal operations remain.

**Abort / escalation.** Abort the rollback and fix forward if: the schema-compatibility guard rejects
the prior build against the migrated schema; `contractBaseline` does not match the expected V1.6.0
baseline; or readiness is DOWN for a reason other than a transient dependency. Escalate to the release
owner before any manual schema change.

**Recovery verification.** After rollback (or successful upgrade), `/actuator/info` shows the expected
`version`/`commit`, `kairo_platform_build_info` matches, and readiness is UP with no `flyway`/`db`
failures. Run the focused M4 acceptance command to confirm health/metrics/support-bundle behaviour on
the rolled-back build:

<!-- OPERATOR-CONFIRMED id="op-m4-focused-upgrade-verify" -->
```bash
mvn -B -ntp -pl kairo-platform-server,kairo-cli,kairo-ops -am test \
  -Dtest='*Health*Test,*Metrics*Test,*SupportBundle*Test' \
  -Dsurefire.failIfNoSpecifiedTests=false
```
<!-- /OPERATOR-CONFIRMED -->
