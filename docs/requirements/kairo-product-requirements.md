# Kairo 产品需求文档（PRD）

> 文档状态：产品与研发基线
> 适用阶段：V1 故障注入闭环
> 更新日期：2026-07-04
> 配套设计：[`../architecture/kairo-platform-web-design.md`](../architecture/kairo-platform-web-design.md)

## 1. 产品定义

Kairo V1 是面向 Java 应用的运行时 Mock 与故障注入平台。系统通过 JVM Agent 在不修改
业务代码的前提下，对指定类和方法应用受控规则；通过中央平台完成 Agent 接入、目标发现、规则
编写、版本管理、发布执行、运行观测和审计。

产品当前面向单组织、单区域的研发、测试与受控生产场景，推荐管理数十至数百个 Agent。
默认使用 Docker Compose 或固定服务器部署，不要求 Kubernetes、企业 SSO、Vault、云 KMS、Kafka
或 MinIO。

## 2. 产品目标与非目标

### 2.1 产品目标

- 让开发者能够安全、直观地创建和验证 Groovy 运行时规则。
- 让运维人员能够查看 JVM/Agent 状态，并控制发布、暂停和回滚。
- 让审计人员能够查询主体、操作、对象、结果和哈希链记录。
- 在不引入 Kubernetes 和企业基础设施的前提下，保持可迁移、可扩展的系统边界。

### 2.2 当前非目标

- 不建设通用 APM、日志检索或全链路追踪平台。
- 不实现完整 OAuth 2.0 Authorization Server。
- 不实现 Keycloak、Okta 或其他企业 SSO 的强制集成。
- 不实现多区域主动—主动和跨区域自动容灾。
- 不把每个领域拆成独立微服务或独立仓库。
- 不允许浏览器直接执行用户 Groovy 脚本。
- 不把 Agent 本地控制台扩展为中央管理平台。
- V1 不交付录制、数据集、数据提取、流量回放和审批工作流；这些能力作为后续阶段重新立项。
- V1 不交付 Kafka Outbox、MinIO 对象归档或独立 Worker 扩缩容。

## 3. 用户角色

| 角色 | 主要目标 | 典型权限 |
| --- | --- | --- |
| 开发者 | 创建、调试和维护规则 | 查看 Agent，编辑规则，执行预览和测试，提交发布 |
| 运维人员 | 保证运行稳定并处理故障 | 管理 Agent、发布计划、命令、暂停、回滚和紧急操作 |
| 审计人员 | 追溯平台操作 | 只读访问审计、发布和结果记录 |
| 平台管理员 | 管理平台与身份 | 管理 Token、权限、系统配置和基础设施状态 |

同一用户可以具有多个角色。权限判断以 Platform API 的资源级 RBAC 为准，前端隐藏按钮不能
替代服务端鉴权。

## 4. 产品形态与运行单元

### 4.1 中央管理平台

`kairo-platform-web` 是独立的现代 Web 前端，采用：

- Next.js App Router；
- React 19；
- TypeScript；
- Tailwind CSS；
- shadcn/ui；
- Lucide 图标；
- Kairo 专属组件；
- Monaco Editor。

它具有独立源码、构建、测试、Docker 镜像和发布周期，通过 Platform API 使用平台能力。
它不是把后端领域拆成新的微服务，而是独立的用户界面和发布边界。

### 4.2 后端与 Agent

- Platform API：认证、RBAC、审计、控制面和查询接口。
- Platform 调度器：发布执行、卸载和运行时租约维护。
- Runtime Agent：目标 JVM 内的方法增强、规则执行、命令轮询和本地降级。
- Agent 本地控制台：仅用于单 JVM 诊断和应急操作，不替代中央管理平台。
- PostgreSQL、Redis：分别承担权威状态和协调。

Platform API 与调度器在 V1 共享同一后端进程。

## 5. 信息架构

平台一级导航如下：

1. 总览
2. 应用与 Agent
3. 规则中心
4. 发布与变更
5. 审计与事件
6. 系统管理

全局区域必须提供：

- 当前环境与平台状态；
- 全局搜索或快捷跳转；
- 失败任务提醒；
- 当前用户、权限与退出；
- 命令面板；
- 页面级帮助和操作反馈。

## 6. 核心用户流程

### 6.1 创建并发布规则

1. 用户选择应用、实例或 Agent。
2. 搜索目标类和方法，确认重载签名。
3. 选择 BEFORE、RETURN 或 THROWS 规则类型。
4. 通过表单配置匹配、采样、命中上限和有效期。
5. 在 Monaco Editor 中编写 Groovy 脚本。
6. 执行语法校验、上下文校验和安全策略检查。
7. 使用示例参数或受控样本执行预览/测试。
8. 查看脚本输出、执行耗时、日志和对象差异。
9. 保存不可变规则版本。
10. 创建发布计划，设置目标范围、批次和失败阈值。
11. 发布计划进入运行态后由调度器下发 Agent 命令。
12. 用户查看实例执行、Agent 命令结果，并在需要时卸载或回滚规则。

## 7. 功能需求

### 7.1 总览

#### DASH-1

展示 Agent 在线状态、活跃规则、进行中发布、最近失败和系统基础设施状态。

#### DASH-2

展示最近失败、最近变更和系统基础设施状态，支持跳转到对应详情。

#### DASH-3

总览数据必须标注更新时间，局部请求失败不得使整个页面不可用。

### 7.2 应用、实例与 Agent

#### AGENT-1

支持按应用、环境、状态、标签和关键字查询实例与 Agent。

#### AGENT-2

Agent 详情至少展示：

- Agent ID、应用、实例、JVM、版本和最后心跳；
- 当前状态和失联时长；
- 已安装规则和最近命令；
- 命令执行结果、错误摘要和审计入口；
- 本地控制台地址仅作为受限诊断信息展示。

#### AGENT-3

高风险命令必须二次确认，并明确目标范围、预期影响和恢复方式。

### 7.3 规则中心

#### RULE-1

支持规则列表、筛选、创建、复制、查看详情和创建新版本。

#### RULE-2

每次保存产生不可变版本。列表和详情必须区分规则身份与规则版本。

#### RULE-3

规则编辑器必须支持：

- Groovy 语法高亮、行号、括号匹配、缩进、搜索和撤销；
- Kairo 上下文变量、方法和模板自动补全；
- 悬浮帮助、代码片段和快捷键说明；
- 服务端语法、安全策略和类型/上下文诊断；
- 错误和警告定位到行列；
- 未保存变更提醒；
- 历史版本只读查看和并排 Diff；
- 编辑区、配置区、诊断区和试运行区可调整布局。

#### RULE-4

前端不得把脚本发送给任何非 Platform API 目标，也不得在浏览器执行 Groovy。

#### RULE-5

脚本测试必须展示输入快照、输出或异常、执行耗时、安全限制、日志摘要和对象差异。

#### RULE-6

发布前必须展示变更 Diff、目标方法、Agent 范围、采样率、命中上限、有效期和风险提示。

#### RULE-7

新建规则采用渐进式流程：

1. 填写规则名称；
2. 从已接入实例中选择应用和环境；
3. 搜索并选择当前范围内已登记的类和方法，必要时由用户明确切换为手动输入；
4. 选择调用前、正常返回后或抛出异常时的执行阶段；
5. 编写脚本、校验并试运行。

生产模式不得默认填入示例规则名称、虚构应用、环境、类名、方法名、业务返回值或测试参数。
初始脚本只能是无副作用的 `return mock.proceed()` 安全骨架。字段未完整时必须禁用校验、
试运行和保存；新建规则必须显示“尚未保存”，不能显示“已保存”。诊断和试运行面板默认
收起，模板只能由用户主动选择。

### 7.4 发布与变更

#### ROLLOUT-1

支持创建发布计划，配置目标、批次、批次间隔、成功条件、失败阈值和回滚策略。

#### ROLLOUT-2

发布状态采用明确状态机，非法状态转换必须被后端拒绝，前端展示可执行动作及原因。

#### ROLLOUT-3

执行页必须展示整体进度、每批次状态、每个 Agent 命令结果和失败原因。

#### ROLLOUT-4

暂停、继续、取消和回滚操作必须具有确认界面、幂等请求和操作反馈。

### 7.5 审计和事件

#### AUDIT-1

审计记录支持按时间、主体、动作、资源和结果查询，并展示哈希链状态。

#### EVENT-1

调度器执行、Agent 命令和发布结果作为运维诊断能力提供，不与普通业务导航混杂。

### 7.6 身份与系统管理

#### AUTH-1

除明确公开的健康检查外，Platform API 必须要求 Bearer Token。

#### AUTH-2

平台不得相信客户端提交的 `X-Actor`、`X-Roles` 或 `X-Identity-Source` 建立身份。

#### AUTH-3

访问令牌必须至少具有 256-bit 随机熵、仅保存哈希、绑定主体、具有有效期、支持撤销并记录审计。

#### AUTH-4

Web 登录在当前阶段接受平台 Token，并通过 Next.js 服务端会话保存。浏览器 JavaScript
不得读取明文 Token，Token 不得进入 URL、localStorage、日志或前端错误上报。

#### AUTH-5

平台需要提供当前主体信息接口，用于返回用户、角色、资源范围和 Token 到期时间。

#### AUTH-6

开发请求头认证只能在显式 `header-dev` 模式和 loopback 来源下启用。

## 8. 交互与视觉需求

### UX-1

产品采用专业、克制、信息密度可调的运维工具视觉，不复刻纪年堂的业务主题；仅复用成熟的
Next.js 工程经验、交互方法和可抽取的设计基础。

### UX-2

使用 Tailwind 设计 Token 和 shadcn/ui 源码组件构建统一设计系统。业务页面不得散落大量
不可复用的任意颜色、圆角和阴影值。

### UX-3

所有异步操作必须提供加载、成功、空状态、部分失败和重试状态。保存、发布、撤销等操作不能
只依赖瞬时 Toast 表达结果。

### UX-4

破坏性或高风险操作使用明确的风险分级：

- 普通操作：直接执行并可撤销；
- 谨慎操作：确认目标和影响；
- 高风险操作：输入确认词、填写原因并记录审计。

### UX-5

桌面端为主要工作区，最低适配宽度 1280 px；1024 px 可完成核心操作；小屏提供只读或简化操作，
不要求在手机上完成复杂脚本编辑。

### UX-6

键盘操作、焦点状态、颜色对比和表单标签应满足 WCAG 2.1 AA 的核心要求。

## 9. 数据、存储与加密需求

### DATA-1

PostgreSQL 是 V1 权威状态源，保存身份、Agent、规则、发布、执行、命令、审计和幂等记录。

### DATA-2

Redis 只保存可重建的短期协调状态。Redis 故障不得破坏数据库权威状态。

### CRYPTO-1

访问 Token 明文只允许在创建或配置注入时出现；数据库仅保存哈希。

### CRYPTO-2

Web 会话密钥只能由部署环境注入，不得进入镜像、日志或前端代码。

## 10. 非功能需求

### PERF-1

- 首次进入应用骨架目标在常规办公网络下 2.5 秒内可交互；
- 普通列表切换和筛选目标在 500 毫秒内出现反馈；
- Monaco Editor 使用动态加载，不阻塞普通页面首屏；
- 10,000 条以上结果必须采用分页或虚拟化。

### REL-1

前端页面局部失败应局部降级；写操作必须有幂等键或防重复提交；网络中断后应保留未保存脚本。

### SEC-1

实施 CSP、点击劫持防护、CSRF 防护、安全 Cookie、依赖锁定和敏感字段脱敏。

### OBS-1

前端错误必须带 request ID、页面和版本信息；不得采集脚本正文、Token、数据源密码或敏感样本。

### COMPAT-1

支持当前两个主要版本的 Chrome 和 Edge。Firefox 为兼容目标，Safari 不是当前复杂编辑场景的
强制验收浏览器。

### TEST-1

- 组件和工具函数使用 Vitest；
- 关键流程使用 Playwright；
- API 类型由 OpenAPI 生成并在 CI 检查漂移；
- 构建必须通过 TypeScript、ESLint、单元测试和生产构建。

## 11. 模块与服务边界需求

### MOD-1

不得以减少模块数量作为重构目标。稳定契约、可替换实现、类加载隔离、独立权限、发行产物和
清晰领域边界均可成为模块存在理由。

### MOD-2

`kairo-platform-web` 具有独立技术栈、用户入口、构建、测试和发布边界，应作为独立模块保留。

### MOD-3

Agent 本地静态控制台只有 Agent Server 一个消费者，继续内嵌在 `kairo-agent-server`，
不得与中央 Platform Web 混为一套产品。

### MOD-4

不得新增与正式 Platform 重复的内存控制面、机械转发服务或无消费者的“预留模块”。

## 12. 部署需求

### DEPLOY-1

Docker Compose 必须能够启动 PostgreSQL、Redis、Platform API、Platform Web、Demo 应用和
attach executor。

### DEPLOY-2

Platform Web 使用独立容器，以 Next.js standalone Node 服务运行；浏览器通过同源 Web/BFF
访问 Platform API，减少 Token 暴露和 CORS 配置。

### DEPLOY-3

生产密钥、Token、Web 会话密钥和后端地址必须由部署环境注入。

### DEPLOY-4

Kubernetes、OIDC、Vault、云 KMS 和云对象存储属于后续可选适配，不是当前验收前提。

## 13. 前后端接口基线

Platform API 已提供完整 Web 所需的真实接口：

- `GET /api/v1/auth/me`：当前主体、角色、范围和 Token 到期时间；
- 规则详情和指定版本查询；
- 脚本校验、预览和受控测试接口；
- 类、方法和签名搜索接口；
- 仪表盘聚合接口；
- 列表统一分页、排序和筛选参数；
- 发布计划、实例执行和 Agent 命令详情接口；
- 必要状态使用短轮询更新，首期不强制 WebSocket。

接口必须先进入 OpenAPI，再生成前端 TypeScript 类型，不允许长期维护手写重复 DTO。

## 14. 版本范围

### V1

- 登录与会话；
- 总览；
- Agent 列表和详情；
- 规则列表、Monaco 编辑、服务端校验、版本保存和 Diff；
- 发布计划和执行状态；
- 审计查询；
- 基础系统状态。

状态：当前发布阶段。

### P1

- 审批工作流；
- 更完整的通知、命令面板和快捷操作；
- 主题切换与用户界面偏好。

状态：后续阶段，不阻塞 V1。

### P2

- 录制、数据集、数据提取；
- 回放、调用结果和比较视图；
- Kafka Outbox、MinIO 对象归档和独立 Worker 扩缩容；

- 云对象存储和云 KMS 适配器；
- 更丰富的可视化、协作和跨环境复制；
- 根据实际规模评估 Kubernetes 部署模板。

## 15. 验收标准

- Platform Web 可以独立构建并通过 Docker Compose 访问。
- 用户 Token 不可被浏览器 JavaScript、URL、localStorage 或日志读取。
- 无权限操作既不展示可操作入口，也会被后端拒绝。
- Monaco Editor 支持 Groovy 高亮、自动补全、服务端诊断、版本 Diff 和未保存提醒。
- 用户可以完成“Agent 接入—选择方法—编辑—校验—测试—保存版本—创建发布—查看结果”的闭环。
- 高风险操作具有确认、原因、审计和失败恢复。
- 大列表采用服务端分页，局部失败不导致整页白屏。
- PostgreSQL 中不出现明文 Token、KEK 或 DEK。
- Maven 后端测试、前端类型检查、单元测试、Playwright 核心流程和 Compose smoke 全部通过。
