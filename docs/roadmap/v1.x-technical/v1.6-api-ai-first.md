# V1.6 技术改造方案：API First 与 AI First

## 1. 目标与当前差距

当前 Platform 已提供 `/api/v1`、Token/RBAC、幂等过滤器、Agent 命令和 OpenAPI 基础；部分 Controller
仍以 `Map<String,Object>` 传递请求响应，Agent 本地 API 也主要由一个路由类集中实现。页面能使用的
能力与适合 AI 完成任务的复合能力尚未形成稳定契约。

本版本冻结公开 API V1，使 Web、CLI、SDK 和 MCP 都成为同一 Platform API 的客户端，并提供带 TTL、
可观察、可撤销的 AI 操作会话。

## 2. API 设计原则

### 2.1 单一控制入口

- 外部客户端只访问 Platform API，不直连 Agent 本地 HTTP。
- Agent 本地协议仍是内部控制协议，可独立版本化，不等同公开 API。
- Web BFF 只处理浏览器会话和代理，不隐藏独有业务逻辑。
- CLI、SDK、MCP 不绕过 RBAC、审计、幂等和风险控制。

### 2.2 强类型契约

- 新 API 使用明确 request/response DTO，逐步替换核心路径上的 Map。
- JSON 字段统一 camelCase；数据库 snake_case 不直接泄漏到 API。
- 每个资源具有稳定 ID、`version`、`createdAt`、`updatedAt`。
- 长操作返回 `operationId`，使用统一 Operation 资源查询。
- 列表统一 cursor 或 page 模型；同一资源族不混用多种分页格式。

### 2.3 写操作协议

所有创建、修改、发布、卸载和会话操作支持：

- `Idempotency-Key`；
- `If-Match` 或 body 中的 expected version；
- correlation ID；
- actor/source；
- dry-run/preview（适用时）；
- 结构化影响范围；
- 机器可读风险等级；
- 撤销或恢复链接。

### 2.4 错误模型

统一响应包含：

- stable code；
- message；
- category；
- retryable；
- field/path/location；
- details；
- suggestedActions；
- correlationId。

禁止 AI 通过解析中文 message 判断错误类型。

## 3. 公开资源模型

建议资源族：

- `/applications`、`/environments`、`/instances`、`/agents`；
- `/classes`、`/methods`、`/call-sites`、`/class-loaders`；
- `/script-policies`、`/script-sessions`；
- `/rules`、`/rule-versions`、`/rule-chains`；
- `/transformation-previews`、`/bytecode-snapshots`、`/bytecode-diffs`；
- `/operations`、`/commands`、`/reconciliations`；
- `/runtime-events`、`/audit-events`、`/diagnostics`。

现有路径保持兼容；不合理路径通过新增资源和 deprecated 标记渐进迁移，不在 V1 中直接删除。

## 4. AI 操作会话

### 4.1 `AutomationSession`

AI/自动化调用的顶层边界，包含：

- session ID、调用主体和来源；
- 应用、环境、实例范围；
- 最大允许 capability profile；
- TTL 和绝对截止时间；
- 创建的脚本会话、规则版本和运行操作；
- 当前风险、状态和清理结果。

会话不是新的权限主体，只能缩小 Token 已有权限，不能扩大权限。

### 4.2 任务级接口

建议提供：

- `POST /api/v1/automation-sessions`；
- `POST /api/v1/automation-sessions/{id}/resolve-targets`；
- `POST /api/v1/automation-sessions/{id}/validate-script`；
- `POST /api/v1/automation-sessions/{id}/preview`；
- `POST /api/v1/automation-sessions/{id}/trial`；
- `POST /api/v1/automation-sessions/{id}/promote`；
- `POST /api/v1/automation-sessions/{id}/revert`；
- `GET /api/v1/automation-sessions/{id}/events`。

自然语言只用于候选搜索和解释，最终增强必须引用稳定 target ID、descriptor、ClassLoader 和预览 revision。
API 不接受“帮我随便找一个支付方法并直接增强”这种不可审计的隐式决策。

### 4.3 AI 上下文包

`resolve-targets` 可返回精简的 `EnhancementContextBundle`：

- 候选方法及置信度和匹配理由；
- 精确 JVM descriptor 和参数/返回类型；
- ClassLoader、代理和兼容等级；
- 可用增强位置和调用点；
- 当前规则链和冲突摘要；
- 允许的脚本档位和限制；
- 脚本 API schema、示例和结构化诊断格式。

上下文包有大小上限和版本号，避免把海量类信息交给模型。

## 5. 模块改造

### 5.1 `kairo-platform-server`

- 按资源拆分当前大 Controller，保持 Controller 只做 HTTP 装配。
- 建立 `api.dto`、应用服务和领域服务边界，核心路径移除 Map 请求。
- 扩展现有 `IdempotencyFilter`，覆盖 body hash、主体、路径和过期策略。
- 建立统一 Operation 服务，收敛 Agent command、发布、回滚、预览等长任务状态。
- 新增 AutomationSession 服务、资源关联、TTL 清理和一键 revert。
- 对 API Token 增加 scope、调用来源和可选会话上限。
- OpenAPI 由代码/契约统一生成或校验，避免手工描述漂移。

建议新增表：

- `automation_session`；
- `automation_session_resource`；
- `api_client` 或扩展 token 元数据；
- `operation_event`（若现有审计/命令表不能满足统一事件流）。

### 5.2 `kairo-agent-server`

- 把单文件路由逐步拆分为 handler/service，但保持内置 HTTP 轻量和 loopback 安全边界。
- 内部协议 DTO 强类型化并增加协议能力协商。
- Agent 注册上报 `protocolVersions` 和 `capabilities`。
- Platform 依据能力选择命令，旧 Agent 收到未知命令前由 Platform 拒绝下发。

### 5.3 `kairo-platform-web`

- 所有数据通过正式 API client。
- 删除仅前端存在的规则拼装、状态推断和错误字符串判断。
- API client 从 OpenAPI 生成类型或通过契约测试保持一致。
- UI 继续提供人工确认，但不拥有 API 客户端无法调用的核心能力。

### 5.4 CLI、SDK 与 MCP

- CLI 覆盖登录配置、目标发现、校验、预览、试用、发布、观察和撤销。
- 至少发布一个官方 SDK；其他语言可由 OpenAPI 生成。
- MCP Server 的 tool 输入输出保持小而结构化，内部只调用 Platform API。
- 危险 tool 默认先 preview，apply 必须携带 preview token/revision。
- MCP 不保存平台超级管理员 Token；使用调用方配置的最小权限 Token。

## 6. API 完整性审计

建立自动化清单：

1. 抓取 Web 使用的所有业务请求；
2. 对照 OpenAPI operation；
3. 检查权限、幂等、错误码和审计覆盖；
4. 检查 CLI/MCP 是否存在 Agent 直连或数据库旁路；
5. 检查每个高风险操作是否提供 preview 和 revert；
6. 检查 deprecated API 是否有替代路径和兼容测试。

## 7. 实施顺序

1. 冻结公开资源、错误、分页、Operation 和写操作协议。
2. 为现有 API 建契约测试，防止改造过程中破坏兼容。
3. 强类型化核心 DTO，补齐 V1.1～V1.5 的公开资源 API。
4. 建立统一 Operation 和 AutomationSession。
5. 迁移 Web 到完整公开 API，完成 API 完整性审计。
6. 发布 CLI 和 SDK。
7. 构建 MCP Server 和 AI 端到端验收场景。

## 8. 测试方案

- OpenAPI 契约：路径、schema、错误码、deprecated 和兼容 diff。
- 幂等：重复 body、不同 body 同 key、不同主体同 key、并发请求。
- 乐观锁：旧 version 修改被拒绝且返回当前状态。
- 权限：用户、管理员、Agent、AI Token scope 的正反矩阵。
- 会话：正常完成、超时、客户端断开、Platform 重启、一键 revert。
- 能力协商：新 Platform/旧 Agent、旧 Platform/新 Agent 的允许组合。
- 客户端：Web、CLI、SDK、MCP 对同一场景返回一致资源状态。
- AI E2E：只提供 Token 和目标意图，完成查找、修正脚本、试用、预览、应用、观察、撤销。

## 9. 验收证据

- Web 请求与 OpenAPI operation 100% 对照报告；
- OpenAPI breaking-change 检查结果；
- CLI 完整生命周期录屏或日志；
- SDK 集成测试；
- MCP 工具列表和无旁路代码审计；
- AI 自动修正一次结构化脚本错误并完成临时增强的日志；
- AI 客户端中断后 Agent 按 TTL 清理的证据；
- 所有写 API 的幂等与乐观锁测试。

## 10. 完成判定

Web 不再拥有私有业务能力，外部客户端无需理解 Agent 内部协议即可完成 V1.X 全生命周期；AI 能通过
结构化上下文和错误完成受控试用并可靠撤销，所有路径共享 RBAC、审计和幂等机制，即判定完成。
