# V1.1 技术改造方案：增强可视化与运行时底座

## 1. 目标与当前差距

当前 `ByteBuddyTransformerManager` 负责安装一个可重置 Transformer，`KairoTransformer` 根据
`InstrumentationRegistry` 中的方法集合织入 Advice。系统能触发 retransformation，但没有权威的
转换输入、输出、修订号和历史，也不能证明卸载后究竟恢复到了哪一份字节码。

本版本建立后续所有增强、组合和恢复能力共同依赖的“字节码事实来源”。

## 2. 技术决策

### 2.1 三类字节码

每次转换都明确记录：

- `inputBytes`：Kairo Transformer 本次收到的输入；
- `plannedBytes`：只读预览生成的预计输出；
- `appliedBytes`：转换完成后，通过临时捕获 Transformer 再次从 JVM 获取的实际字节码。

不把磁盘 class 文件或 Agent 首次启动时看到的字节码直接称为“原始字节码”。其他 Agent 的顺序会让
这个概念产生歧义。页面可显示“本次增强前”，底层字段必须使用 `INPUT`、`PLANNED`、`APPLIED`。

### 2.2 快照存储

- Agent 内使用有上限的本地快照仓库，按 `ClassIdentity + TransformationRevision + kind` 索引。
- 原始 bytes 默认不长期写入 Platform 数据库；Platform 保存元数据、哈希和按需获取引用。
- 导出或持久化 class bytes 必须显式调用，设置大小、数量和保留时间上限。
- 快照不得强引用 `Class<?>` 或 ClassLoader，使用稳定 ID 和弱引用辅助定位。

### 2.3 反编译与 Diff

- 新建 `BytecodeDecompiler` SPI，默认实现选择支持当前 JDK 矩阵的反编译器。
- 反编译器运行在 Agent 控制线程池之外的有界诊断执行器，不能占用业务线程。
- Java Diff 仅用于可读性；ASM tree 规范化后的指令 Diff 用于权威比较。
- 规范化时忽略 constant-pool 下标等无语义噪声，但保留指令、描述符、栈帧、异常表和属性差异。

## 3. 模块改造

### 3.1 `kairo-api` / 协议模块

新增或等价实现：

- `ClassIdentity`；
- `BytecodeSnapshotKind`；
- `BytecodeSnapshotMetadata`；
- `TransformationRevision`；
- `TransformationStatus`；
- `BytecodeDiffResult`；
- `TransformationDiagnostic`。

这些 DTO 不包含 Byte Buddy、ASM 或反编译器类型。

### 3.2 `kairo-agent-core`

新增建议组件：

- `BytecodeSnapshotRepository`：有界、并发安全、支持 TTL；
- `TransformationJournal`：记录转换开始、成功、失败、验证和恢复；
- `CapturingTransformer`：短生命周期、只捕获目标类实际 bytes；
- `TransformationPreviewService`：使用和正式转换相同的转换计划生成预计结果；
- `BytecodeVerificationService`：校验 class 格式、哈希和结构 Diff；
- `DecompilerService`：隔离反编译器并限制输入大小、并发和超时。

改造 `ByteBuddyTransformerManager`：

- 安装时注入转换监听器；
- 每次目标类转换分配单调 revision；
- 记录输入哈希、输出哈希和失败信息；
- `retransform` 返回逐类结果，不再只返回 void；
- `close/reset` 也进入转换日志。

改造 `KairoTransformer`：

- 转换逻辑从“读取 registry 后直接 visit”拆成可复用的 `TransformationPlan`；
- 正式应用和只读预览复用相同 plan；
- 输出目标匹配数量、Advice 类型和增强位置元数据。

### 3.3 `kairo-agent-server`

Agent 本地 API 建议增加：

- `GET /v1/classes/{classId}/transformations`；
- `GET /v1/classes/{classId}/bytecode?kind=&revision=`；
- `POST /v1/classes/{classId}/preview`；
- `POST /v1/classes/{classId}/capture`；
- `GET /v1/classes/{classId}/diff?from=&to=&format=`。

字节码二进制使用 `application/octet-stream`；元数据和 Diff 使用 JSON。大响应必须限制体积。

### 3.4 `kairo-platform-server`

- 增加字节码诊断代理服务，不让浏览器直连 Agent。
- 新增转换元数据表，至少包含 agent、class identity、revision、kind、hash、size、status、时间和诊断。
- 默认不保存二进制；如启用持久化，使用独立 blob SPI，不能塞入审计事件 JSON。
- 记录预览和导出操作审计。

### 3.5 `kairo-platform-web`

- 新增增强对比视图，支持源码近似 Diff、字节码 Diff 和元数据。
- 清晰区分“预览”和“JVM 实际运行”。
- 展示 ClassLoader、revision、哈希、采集时间和反编译器。
- 反编译失败时自动降级到字节码视图。

## 4. 实施顺序

1. 冻结 `ClassIdentity`、revision 和快照语义。
2. 实现 Agent 快照仓库、转换日志和逐类转换结果。
3. 把当前 Kairo 转换拆成可预览的 plan。
4. 实现实际字节码捕获和结构验证。
5. 接入反编译器与两类 Diff。
6. 增加 Agent/Platform API、数据库迁移和 Web。
7. 补齐限制、清理、审计和端到端测试。

## 5. 测试方案

- 单元：快照 TTL/LRU、revision 并发、Diff 规范化、大小限制。
- Agent 集成：增强前捕获、预览不生效、正式增强、局部卸载、完全恢复。
- 多 ClassLoader：同名类生成不同快照且查询不串数据。
- 共存烟雾：Kairo 前后各安装一个测试 Transformer，确认 input/applied 语义。
- 故障：反编译超时、非法 class、类不可修改、retransform 失败。
- 性能：快照关闭和开启时分别测空载开销；反编译不得进入调用链。

## 6. 验收证据

开发智能体必须提交：

- `mvn test` 及新增端到端测试结果。

## 7. 完成判定

路线图 V1.1 的全部验收项通过；后续版本能够仅依赖公开的转换计划、快照和 revision 契约，
无需直接读取 `ByteBuddyTransformerManager` 私有状态，即判定完成。

## 8. 第二阶段实现状态与设计决策

本节记录 V1.1 第二阶段（TransformationPlan、TransformerManager 改造、实际捕获、预览与字节码 Diff）
落地后的真实实现位置与关键决策，供后续版本依赖。HTTP/Platform/Web 与反编译器依赖按约定不在本阶段引入。

### 8.1 组件落点

- `TransformationPlan`（`kairo-agent-core`）：不可变。`TransformationPlan.from(registry, className, classLoaderId)`
  解析 registry -> `MethodMatchers` -> void/value Advice 选择；`apply(DynamicType.Builder<?>)` 织入。
  正式 `KairoTransformer` 与只读 `TransformationPreviewService` 都调用同一 `from` + `apply`，V1.0 织入行为不变。
- `ByteBuddyTransformerManager`（`kairo-agent-core`）改造：
  - `InputCaptureTransformer`（原始 `ClassFileTransformer`，`canRetransform=true`）在 Kairo 之前安装，
    记录本次 INPUT bytes、计算 SHA-256、存 INPUT 快照、通过 `TransformationJournal.nextRevision` 分配单调 revision、
    记录 STARTED；返回 `null` 不改变输入；
  - `AgentBuilder.Listener`（`onTransformation`/`onError`/`onIgnored`）记录 OUTPUT 哈希、关闭日志条目、
    产出结构化逐类 `TransformationResult`；
  - `captureApplied(Class)` 通过短生命周期 `CaptureOnlyTransformer`（try/finally 移除）再次从 JVM 获取 APPLIED bytes，
    不推进 revision，不把任何 bytes 当作“最初字节码”去覆盖其他 Transformer；
  - `retransform(Class...)` 返回 `List<TransformationResult>`（V1.0 `void` 调用方忽略结果即兼容）；
  - `close()` 卸载 inputCapture 与 resettable transformer 并记录 RECOVERY。
- `BytecodeCaptureService`：调用 `captureApplied` 取回实际 bytes，存 APPLIED 快照并校验 hash 与最近一次 transform 输出一致。
- `TransformationPreviewService`：`TransformationPlan.from(...)` + 离线 `ByteBuddy.redefine(td, ClassFileLocator).make()`
  生成 PLANNED bytes，存 PLANNED 快照（当前 revision，不推进），不调用 `retransformClasses`、不改 JVM。
- `BytecodeDiffService` + `BytecodeNormalizer`（`kairo-agent-core.bytecode.diff`）：见 8.2。
- `BytecodeDecompiler` SPI + `DecompilationResult`/`DecompilationStatus`（`kairo-api.bytecode`，纯类型，无 ASM/Byte Buddy 依赖）；
  `UnavailableBytecodeDecompiler`（`kairo-agent-core`）诚实返回 `UNAVAILABLE`，绝不伪称成功；
  `DecompilerService` 在独立有界守护线程池上执行，带超时与体积上限。
- `AgentRuntime`：构造并接线上述全部服务；`start()` 调度规则 TTL（1s）与快照 `evictExpired`（5s）；
  `close()`/`resetAll()` 释放 transformer、decompiler、snapshotRepository 与执行器。只读服务通过
  `previewService()`/`captureService()`/`diffService()`/`decompilerService()`/`snapshotRepository()`/`transformationJournal()`
  暴露，供下一阶段 HTTP 层在控制线程上调用。

### 8.2 关键设计决策

- **Byte Buddy shaded ASM 无 `tree` 包**：`byte-buddy` 1.17.x 的 shaded ASM 仅包含 core（`ClassReader`/`ClassVisitor`/
  `MethodVisitor`/`Opcodes`/`Type`/`Label`）和最小 `commons`，不含 `tree`（无 `ClassNode`/`MethodNode`）。
  因此 `BytecodeNormalizer` 用 core visitor API 构建规范化模型，语义等价于 tree 规范化。
- **规范化忽略无语义噪声**：constant-pool 下标从不暴露给 visitor（只有解析后的 owner/name/desc）；
  `ClassReader.SKIP_FRAMES` 跳过栈帧（帧是指令的确定性函数，跨 `disableClassFormatChanges` 补丁与全量重写会产生假 diff）；
  `ClassReader.SKIP_DEBUG` 跳过行号/源文件/局部变量名；`Label` 按首次出现顺序归一为 `L0/L1/...`。
  保留指令、描述符、签名、异常表、注解、类/字段结构。真实 Advice 修改（新增指令 + `onThrowable` try-catch）会被识别。
- **重变换幂等性与 INPUT 语义**：经真实 JVM 验证，`ResettableClassFileTransformer` 在每次 retransform 开始时
  先复位到其捕获的“原始”字节再织入，因此对已增强类重复 retransform 幂等（不二次包装）。`InputCaptureTransformer`
  在链首观测到的正是 Kairo 本次收到的 INPUT（即复位后的字节），故 INPUT 稳定且诚实，但不等同于“磁盘 class”或
  “Agent 启动字节”——其他 Agent 的安装顺序会让该概念产生歧义，这正是本阶段只使用 INPUT/PLANNED/APPLIED 的原因。
- **三类字节码各自来源**：INPUT=InputCapture 链首捕获；PLANNED=离线 plan；APPLIED=转换后短生命周期捕获再取。
  任何 bytes 都不被当作“最初字节码”用于覆盖其他 Transformer。
- **preview 不在业务线程**：`TransformationPreviewService` 不调用 `Instrumentation`、不改 JVM，且被设计为在控制/诊断线程
  调用；慢路径反编译由 `DecompilerService` 在自有有界执行器上运行。本阶段无 HTTP 入口，下一阶段 HTTP 层须将
  preview/capture/diff/decompile 派发到控制线程。

### 8.3 测试证据

`mvn -pl kairo-integration-tests -am clean test` 全绿（34 个集成测试 + 全部上游单元测试）。
`BytecodeVisibilityIntegrationTest`（9 项）覆盖：预览不触 JVM、四哈希（增强前/预览/实际/卸载）、
journal 历史与 reset/recovery、逐类 retransform 结果、结构化失败诊断、双 ClassLoader 同名类隔离、
前后测试 Transformer 共存、反编译 UNAVAILABLE 诊断、快照有界与清理。
`BytecodeDiffServiceTest`（5 项单元）覆盖：相同字节相同、constant-pool 重排不产生假 diff、真实指令变更被识别、
null 与非法字节降级为 `normalized=false`。

### 8.4 下一阶段（V1.2/HTTP）可调用接口

`AgentRuntime` 暴露的只读服务方法（在控制线程上调用）：
`previewService().preview(ClassIdentity, byte[])`、`captureService().capture(Class<?>)`、
`diffService().diff(...)`、`decompilerService().decompile(ClassIdentity, byte[])`、
`snapshotRepository()`/`transformationJournal()` 快照与日志查询、`transformerManager().currentRevision(ClassIdentity)`。
HTTP 路由（`GET /v1/classes/{id}/transformations`、`.../bytecode`、`POST .../preview`、`.../capture`、`GET .../diff`）
与 Platform 代理/数据库/Web 属下一阶段，本阶段不实现。
