# V1.1 技术改造方案：增强可视化与运行时底座

## 1. 目标与当前差距

当前 `ByteBuddyTransformerManager` 负责安装一个可重置 Transformer，`KairoTransformer` 根据
`InstrumentationRegistry` 中的方法集合织入 Advice。系统能触发 retransformation，但没有权威的
转换输入、输出、修订号和历史，也不能证明卸载后究竟恢复到了哪一份字节码。

本版本建立后续所有增强、组合和恢复能力共同依赖的“字节码事实来源”。

## 2. 技术决策

### 2.1 三类字节码

每次转换都明确记录：

- `inputBytes`：Kairo Transformer 本次收到的输入；
- `plannedBytes`：只读预览生成的预计输出；
- `appliedBytes`：转换完成后，通过临时捕获 Transformer 再次从 JVM 获取的实际字节码。

不把磁盘 class 文件或 Agent 首次启动时看到的字节码直接称为“原始字节码”。其他 Agent 的顺序会让
这个概念产生歧义。页面可显示“本次增强前”，底层字段必须使用 `INPUT`、`PLANNED`、`APPLIED`。

### 2.2 快照存储

- Agent 内使用有上限的本地快照仓库，按 `ClassIdentity + TransformationRevision + kind` 索引。
- 原始 bytes 默认不长期写入 Platform 数据库；Platform 保存元数据、哈希和按需获取引用。
- 导出或持久化 class bytes 必须显式调用，设置大小、数量和保留时间上限。
- 快照不得强引用 `Class<?>` 或 ClassLoader，使用稳定 ID 和弱引用辅助定位。

### 2.3 反编译与 Diff

- 新建 `BytecodeDecompiler` SPI，默认实现选择支持当前 JDK 矩阵的反编译器。
- 反编译器运行在 Agent 控制线程池之外的有界诊断执行器，不能占用业务线程。
- Java Diff 仅用于可读性；ASM tree 规范化后的指令 Diff 用于权威比较。
- 规范化时忽略 constant-pool 下标等无语义噪声，但保留指令、描述符、栈帧、异常表和属性差异。

## 3. 模块改造

### 3.1 `kairo-api` / 协议模块

新增或等价实现：

- `ClassIdentity`；
- `BytecodeSnapshotKind`；
- `BytecodeSnapshotMetadata`；
- `TransformationRevision`；
- `TransformationStatus`；
- `BytecodeDiffResult`；
- `TransformationDiagnostic`。

这些 DTO 不包含 Byte Buddy、ASM 或反编译器类型。

### 3.2 `kairo-agent-core`

新增建议组件：

- `BytecodeSnapshotRepository`：有界、并发安全、支持 TTL；
- `TransformationJournal`：记录转换开始、成功、失败、验证和恢复；
- `CapturingTransformer`：短生命周期、只捕获目标类实际 bytes；
- `TransformationPreviewService`：使用和正式转换相同的转换计划生成预计结果；
- `BytecodeVerificationService`：校验 class 格式、哈希和结构 Diff；
- `DecompilerService`：隔离反编译器并限制输入大小、并发和超时。

改造 `ByteBuddyTransformerManager`：

- 安装时注入转换监听器；
- 每次目标类转换分配单调 revision；
- 记录输入哈希、输出哈希和失败信息；
- `retransform` 返回逐类结果，不再只返回 void；
- `close/reset` 也进入转换日志。

改造 `KairoTransformer`：

- 转换逻辑从“读取 registry 后直接 visit”拆成可复用的 `TransformationPlan`；
- 正式应用和只读预览复用相同 plan；
- 输出目标匹配数量、Advice 类型和增强位置元数据。

### 3.3 `kairo-agent-server`

Agent 本地 API 建议增加：

- `GET /v1/classes/{classId}/transformations`；
- `GET /v1/classes/{classId}/bytecode?kind=&revision=`；
- `POST /v1/classes/{classId}/preview`；
- `POST /v1/classes/{classId}/capture`；
- `GET /v1/classes/{classId}/diff?from=&to=&format=`。

字节码二进制使用 `application/octet-stream`；元数据和 Diff 使用 JSON。大响应必须限制体积。

### 3.4 `kairo-platform-server`

- 增加字节码诊断代理服务，不让浏览器直连 Agent。
- 新增转换元数据表，至少包含 agent、class identity、revision、kind、hash、size、status、时间和诊断。
- 默认不保存二进制；如启用持久化，使用独立 blob SPI，不能塞入审计事件 JSON。
- 记录预览和导出操作审计。

### 3.5 `kairo-platform-web`

- 新增增强对比视图，支持源码近似 Diff、字节码 Diff 和元数据。
- 清晰区分“预览”和“JVM 实际运行”。
- 展示 ClassLoader、revision、哈希、采集时间和反编译器。
- 反编译失败时自动降级到字节码视图。

## 4. 实施顺序

1. 冻结 `ClassIdentity`、revision 和快照语义。
2. 实现 Agent 快照仓库、转换日志和逐类转换结果。
3. 把当前 Kairo 转换拆成可预览的 plan。
4. 实现实际字节码捕获和结构验证。
5. 接入反编译器与两类 Diff。
6. 增加 Agent/Platform API、数据库迁移和 Web。
7. 补齐限制、清理、审计和端到端测试。

## 5. 测试方案

- 单元：快照 TTL/LRU、revision 并发、Diff 规范化、大小限制。
- Agent 集成：增强前捕获、预览不生效、正式增强、局部卸载、完全恢复。
- 多 ClassLoader：同名类生成不同快照且查询不串数据。
- 共存烟雾：Kairo 前后各安装一个测试 Transformer，确认 input/applied 语义。
- 故障：反编译超时、非法 class、类不可修改、retransform 失败。
- 性能：快照关闭和开启时分别测空载开销；反编译不得进入调用链。

## 6. 验收证据

开发智能体必须提交：

- 一个普通方法增强前、预览、实际运行、卸载后的四份哈希及 Diff；
- 一个双 ClassLoader 同名类用例；
- 一个其他测试 Transformer 共存用例；
- 快照上限和清理测试；
- Agent 与 Platform API 示例；
- `mvn test` 及新增端到端测试结果。

## 7. 完成判定

路线图 V1.1 的全部验收项通过；后续版本能够仅依赖公开的转换计划、快照和 revision 契约，
无需直接读取 `ByteBuddyTransformerManager` 私有状态，即判定完成。
