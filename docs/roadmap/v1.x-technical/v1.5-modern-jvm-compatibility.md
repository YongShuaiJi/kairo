# V1.5 技术改造方案：现代 JVM 场景兼容

## 1. 目标与当前差距

当前 `LoadedClassRepository` 和 `DefaultInstrumentationRegistry` 已使用 ClassLoader ID 辅助区分同名类，
但 Transformer 默认忽略 `java.*`、`jdk.*` 等类型，`AgentRuntime.publish` 拒绝 synthetic/bridge 方法，
尚未形成代理目标解析、未加载类预注册、类重定义后对账和 ClassLoader 回收机制。

本版本不新增增强业务语义，只让 V1.4 已冻结的语义在复杂 JVM 环境中准确工作。

## 2. 支持等级

每个兼容场景必须标记：

- `SUPPORTED`：持续集成覆盖，承诺增强和卸载；
- `LIMITED`：明确限制，有自动化或人工验证；
- `EXPERIMENTAL`：可启用但不进入稳定承诺；
- `UNSUPPORTED`：发布前拒绝并说明原因。

不能用“理论上 Byte Buddy 支持”代替 Kairo 的支持声明。

## 3. ClassIdentity 与生命周期

### 3.1 身份信息

扩展 V1.1 的 `ClassIdentity` 元数据：

- binary class name；
- 稳定的运行期 classLoaderId；
- loader class name；
- parent loader ID；
- Java module name/named 状态；
- code source；
- protection domain 摘要；
- 当前字节码 hash。

classLoaderId 只保证单次 JVM 生命周期内唯一。跨 JVM 重启的规则通过应用、类名、loader selector 和
code source 重新解析，不能假定旧 ID 永久有效。

### 3.2 引用管理

- 反射 Method、Class 和 ClassLoader 不得长期作为 Platform 身份。
- Agent 缓存使用弱键/弱引用或显式生命周期清理。
- 规则运行需要的强引用必须随规则链卸载释放。
- ReferenceQueue 清理后同步删除快照、编译缓存、方法缓存和运行统计。

## 4. 兼容子系统

### 4.1 多 ClassLoader

- 类搜索返回全部候选，不默认选择第一个。
- 精确发布必须携带当前 JVM classLoaderId。
- 模糊 selector 仅用于未加载类预注册，匹配多项时按策略拒绝或显式 all-match。
- 支持 Bootstrap loader 的特殊 ID，并将 JDK 类增强设置为单独高风险能力；不能简单删除 ignore 列表。
- Spring Boot、Tomcat 和插件 ClassLoader 建立识别适配器，但核心身份不依赖框架类。

### 4.2 代理目标解析

新增 `ProxyTargetAnalyzer` SPI，输出：

- 当前类类型：JDK proxy、CGLIB、Byte Buddy、普通类或未知；
- 代理接口/父类；
- 候选用户方法；
- 推荐增强目标；
- 增强代理类、目标类或二者的影响解释。

系统不应擅自从代理类跳转到目标类后发布，最终选择必须进入规则目标和审计。

### 4.3 synthetic、bridge 与 Lambda

- 取消当前一刀切拒绝，改为发现时标记、策略控制和精确描述符匹配。
- bridge 方法默认提示增强用户声明方法，显式选择后可以增强。
- Lambda 类名和生命周期不稳定，优先支持对包含 invokedynamic 的声明方法或稳定生成类实例进行增强。
- Lambda 兼容按 JDK 版本建立测试，不承诺跨重启复用旧生成类名。

### 4.4 未加载类与重新定义

- 新增 `PendingEnhancementRegistry`，保存基于 loader selector 的预注册规则。
- Transformer 在首次加载匹配类型时生成 V1.4 规则链并报告实际 identity。
- 监听 redefine/retransform 结果；字节码 hash 变化时重新验证调用点 fingerprint。
- 热更新后若目标仍兼容，应用新 transformation revision；不兼容则保持 fail-open 并标记 `TARGET_DRIFTED`。

### 4.5 Java Module

- 发现并报告 named module 和包开放状态。
- Advice/Bridge 访问失败时给出 module 诊断。
- 需要 `Instrumentation.redefineModule` 时采用最小开放集合并审计，不做全局开放。
- Bootstrap 注入依赖继续通过 `kairo-bootstrap-api`，避免业务类直接链接 Agent 实现。

## 5. 模块改造

### `kairo-agent-core`

- 扩展 `LoadedClassRepository` 为生命周期感知仓库。
- 增加 `ClassLoaderRepository`、ReferenceQueue 清理器和 module 诊断。
- 增加代理分析、pending registry、首次加载匹配和热更新对账。
- `ByteBuddyTransformerManager.ignore` 改为策略对象，支持受控的 Bootstrap/JDK 类范围。
- 所有 registry、snapshot、script cache 使用统一 ClassIdentity。

### `kairo-platform-server`

- 目标发现数据保存 loader/module/code source 元数据和最后观察时间。
- 规则预注册使用 `ClassSelector`，实际发布产生实例级 `ResolvedTarget`。
- 同名候选多于一个时 API 返回 `AMBIGUOUS_TARGET`，除非调用者显式 all-match。
- 保存兼容等级、诊断和热更新后的漂移状态。

### `kairo-platform-web`

- 类选择器展示 loader 树、module、code source 和代理类型。
- 明确区分“声明类”“代理类”“实际增强类”。
- Lambda、synthetic、bridge 和 JDK 类显示风险与支持等级。

## 6. 自动化兼容矩阵

构建独立测试工程/fixture，矩阵至少包含：

- JDK 8、11、17、21；
- premain、agentmain、attach；
- Spring Boot 2.x、3.x；
- 普通自定义 ClassLoader、父子同名类；
- Tomcat 风格 WebApp ClassLoader；
- JDK Proxy、CGLIB、Spring AOP；
- Lambda、bridge、synthetic；
- 类首次加载、retransform、redefine 和模拟热更新；
- Java module 开放/未开放；
- Kotlin 普通方法、默认参数；协程按验证结果标记等级。

CI 可按快速矩阵和夜间完整矩阵拆分，但正式发布必须提供完整矩阵结果。

## 7. 实施顺序

1. 冻结支持等级和扩展后的 ClassIdentity。
2. 统一 Agent 内所有 ClassLoader 相关缓存及清理。
3. 完成多 loader 精确选择和 Bootstrap/module 诊断。
4. 实现代理分析和 synthetic/bridge 策略。
5. 实现未加载类预注册与热更新对账。
6. 建立 Lambda、框架和语言矩阵。
7. 接入 Platform/Web 并完成完整矩阵回归。

## 8. 验收证据

- 完整兼容矩阵报告，含支持等级和失败原因；
- 父子 ClassLoader 同名类只增强指定目标的证据；
- 代理类与目标类分别增强的行为和 Diff；
- 未加载类首次加载后自动应用规则；
- 热更新后成功重新增强或明确漂移失败；
- ClassLoader 回收的弱引用/堆分析证据；
- V1.4 规则链、精确卸载和其他 Agent 共存无回归。

## 9. 完成判定

正式矩阵全部自动化通过，有限/实验/不支持范围有明确文档；任何选择歧义、目标漂移和模块访问失败
都不会静默增强错误目标，即判定完成。
