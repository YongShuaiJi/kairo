# V1.4 技术改造方案：多规则增强链与可靠恢复

## 1. 目标与当前差距

当前 `RuleRegistry` 已能在一个 `MethodKey` 下保存多个 `CompiledRule`，`RuleSet` 也能按阶段和优先级
取规则，但 `RuleDispatcher` 遇到首个非 PROCEED 决策即返回，尚未形成可版本化、可解释、可冲突检测
的正式规则链。`AgentRuntime` 的发布与删除通过方法级 retransformation 补偿，`resetAll` 会重置整个
Transformer，不能作为多 Agent 环境中的精确恢复协议。

本版本建立不可变规则链快照、确定执行语义、事务式应用、状态对账和精确卸载。

## 2. 规则链规范

### 2.1 排序

规范排序键固定为：

`priority DESC, createdAt ASC, ruleId ASC`。

Platform 和 Agent 均使用同一规范化算法；链哈希基于规范化 JSON 计算。不得依赖数据库自然顺序或
ConcurrentHashMap 遍历顺序。

### 2.2 数据传递

- BEFORE：每条 PROCEED 规则输出的参数成为下一条规则输入。
- RETURN：当前返回值按链顺序传递；替换结果后可由后续规则继续观察。
- THROWS：当前异常按链顺序传递；规则可替换异常或恢复为返回值。
- FINALLY：观察前面阶段结束后的当前 outcome。
- CALL 阶段遵循相同的参数与 outcome 传递模型。

状态中同时保留 original 与 current，脚本必须明确读取哪一个。

### 2.3 传播控制

脚本决策扩展为：

- `CONTINUE`：采用当前修改并继续后续规则；
- `TERMINATE`：采用当前 outcome，终止当前阶段规则链；
- `PROCEED_ORIGINAL`：只对进入/调用前位置有效，继续真实执行；
- `FAIL_OPEN`：丢弃当前规则修改并继续；
- `FAIL_CLOSED` 不作为默认能力，若保留必须由应用策略显式允许。

旧 `MockDecision.proceed/return/throw` 映射到兼容语义，并在文档中固定，不能随实现猜测。

### 2.4 冲突

静态冲突至少识别：

- 多个无条件终止规则；
- 不可达规则；
- 互斥组同时启用；
- 相同调用点的独占替换；
- 能力档位超过应用上限；
- 目标 revision 或调用点 fingerprint 漂移。

无法静态判断业务条件是否重叠时标记 `POTENTIAL`，由用户显式确认，不假装精确证明。

## 3. 版本与状态模型

### 3.1 期望状态

Platform 保存每个 `agent + enhancement target` 的 `RuleChainSpec`：

- chain ID；
- 单调 revision；
- 规范化 hash；
- 规则版本列表和顺序；
- 目标转换 revision；
- 期望状态 `ACTIVE/EMPTY`。

### 3.2 实际状态

Agent 保存不可变 `RuleChainSnapshot` 并通过原子引用替换：

- applied revision/hash；
- compiled rule 列表；
- transformation revision/hash；
- apply time；
- degraded reason。

业务线程只读取不可变快照，不参与编译、转换、数据库或网络操作。

### 3.3 命令 fencing

每个 APPLY/REMOVE/RECONCILE 命令携带：

- command ID 和 idempotency key；
- expected current revision；
- desired revision 和 desired hash；
- target identity；
- deadline；
- 完整期望链或内容寻址引用。

Agent 只接受合法的 revision 转换。旧命令返回 `STALE_COMMAND`，重复命令返回先前结果。

## 4. 模块改造

### 4.1 `kairo-api` 和 `kairo-core`

新增：

- `RuleChainSpec`、`RuleChainRevision`、`RuleChainSnapshot`；
- `RuleChainDecision`、`PropagationMode`、`OutcomeState`；
- `ConflictReport`、`ConflictSeverity`；
- `ApplyChainRequest/Result`、`ReconcileResult`。

重构 `RuleRegistry`：

- 权威 key 从单纯 `MethodKey` 升级为 `EnhancementTarget`；
- 提供 CAS 替换整个不可变链，不逐条原地修改；
- 快照携带 revision/hash；
- 保留旧方法作为兼容适配层，逐步删除双写。

重构 `RuleDispatcher`：

- 实现规范化链状态机；
- 分离脚本执行、决策校验和 outcome 合并；
- 每次调用固定读取一个链快照，调用中途发布新链不影响本次执行；
- 记录命中的 chain revision，便于审计和问题复现。

### 4.2 `kairo-agent-core`

- `AgentRuntime.publish/remove` 收敛为 `applyRuleChain`。
- 编译完整期望链后再执行转换，任何编译失败不修改当前快照。
- 转换成功并经 V1.1 实际字节码验证后，才原子切换运行快照。
- 若只改变规则内容而增强位置未变，尽量只替换链快照，不触发 retransformation。
- 只有目标位置集合从空到非空或发生位置变化时才重转换类。
- 精确卸载以“重新生成剩余 Kairo 增强计划”实现，不用 reset 全部 Transformer。
- 增加 Agent 本地幂等结果缓存和对账快照接口。

### 4.3 `kairo-platform-server`

新增或调整表：

- `rule_chain_desired_state`；
- `rule_chain_instance_state`；
- `rule_chain_operation`；
- `rule_chain_operation_target`；
- 命令表增加 expected/desired revision 和 result hash。

发布流程：

1. 读取目标当前期望链；
2. 合并规则并规范化；
3. 执行冲突分析；
4. CAS 写入新期望 revision；
5. 向各 Agent 下发完整期望链；
6. 根据实际 revision/hash 收敛操作状态；
7. 部分失败时按策略保持旧链或向成功实例下发旧链回滚。

卸载是生成“不包含目标规则的新期望链”，不是 `RESET_ALL`。现有自动卸载逻辑中使用 `RESET_ALL`
的路径必须改造为精确链回滚。

### 4.4 其他 Agent 共存

- 使用 V1.1 的本次转换 input 作为当前基线，不缓存并强写 JVM 启动时 bytes。
- 重新转换时只声明 Kairo 自己的 visitor，不主动移除未知 Advice。
- 建立测试 Transformer，可配置在 Kairo 前后安装并插入可检测标记。
- 对无法保证 retransformation 顺序或其他 Agent 不支持重转换的情况返回 `COEXISTENCE_UNSAFE`。
- `resetAll` 仅清空 Kairo 期望链并按类重新生成，不通过 transformer.reset 粗暴声明成功。

## 5. 实施顺序

1. 冻结规则排序、传播、original/current 和兼容映射语义。
2. 实现不可变链、hash、冲突分析和 Dispatcher 状态机。
3. 将 Agent 单规则命令迁移为完整链 apply，保留旧协议适配。
4. 实现 expected/desired revision fencing 和幂等结果。
5. 改造 Platform 期望/实际状态与精确卸载。
6. 实现断线重连对账和多目标回滚。
7. 完成其他 Agent 共存矩阵、压力和确定性测试。

## 6. 测试矩阵

- 组合：参数逐条修改、返回逐条修改、异常替换、异常恢复、FINALLY。
- 传播：continue、terminate、fail-open、短路和互斥。
- 并发：调用过程中切链、两个发布并发、发布与卸载并发。
- 幂等：重复、乱序、超时重发、旧命令晚到。
- 事务：多方法第二个失败、Agent 在转换前/后/确认前退出。
- 恢复：局部卸载、最后一条卸载、离线后重连、Platform 重启。
- 共存：测试 Transformer 位于 Kairo 前后，另加至少两种真实工具组合。
- 压力：至少 1,000 次组合/局部卸载；长期目标 10,000 次进入 V1.7。

## 7. 验收证据

- 规则链规范和旧决策映射测试；
- 同一调用固定使用一个 snapshot 的并发证据；
- 乱序命令被 fencing 拒绝的日志和 API 结果；
- 卸载中间规则后其他规则仍生效的字节码及行为证据；
- 自动卸载不再使用 `RESET_ALL` 的代码证据；
- 其他 Agent 标记在 Kairo 卸载后仍存在的验证；
- 1,000 次循环最终 hash 一致报告。

## 8. 完成判定

Platform 期望链、Agent 实际链和 JVM 实际字节码三者可通过 revision/hash 对账；任意规则可精确卸载，
乱序操作不会破坏新状态，共存矩阵中其他 Agent 的修改被保留，即判定完成。
