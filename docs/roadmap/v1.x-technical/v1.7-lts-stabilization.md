## 1. 唯一版本目标

V1.1～V1.6 已经完成字节码观察、脚本能力、增强位置、规则链、现代 JVM 目标解析和 API/AI
自动化能力。V1.7 不再回答“还能增强什么”，只回答以下四个发布问题：

1. **不会错做**：重复、延迟、乱序和旧 owner 的命令不能覆盖新状态，完成过的正式操作不会重复执行。
2. **能够恢复**：Platform、Agent 或目标 JVM 重启后，正式规则能够按平台期望状态重新收敛；临时规则不会错误复活。
3. **不会拖垮目标 JVM**：真实增强/卸载循环、脚本和 ClassLoader 生命周期不存在持续资源漂移或不可接受退化。
4. **能够正式交付**：版本、支持矩阵、健康状态、发布物和验收证据真实一致，用户能够判断风险并完成恢复。

V1.7.0 的一句话完成标准是：

> 在本文明确支持的单 Platform 拓扑和 JVM 组合中，Kairo 经受重启、断连、重试、乱序、卸载和长稳验证后，
> 仍能保持方法实际行为、规则状态、字节码 revision/hash 与平台权威状态一致，并能从干净源码生成可验证发布物。

## 2. 当前代码事实

以下内容是实施输入，不允许开发智能体忽略后重新设计一套系统。

### 2.1 已经完成的能力

- `kairo-core` 已有不可变规则集、原子替换、采样、命中上限、重入保护和 fail-open。
- `kairo-agent-core` 已有真实 Instrumentation、规则链 CAS、转换 revision/hash、精确卸载、字节码快照、
  ClassLoader 生命周期清理、代理/Lambda/bridge/synthetic 处理和热更新漂移识别。
- `kairo-agent-server` 已有 Agent 本地 API、平台注册、心跳、命令轮询、协议 capability 和本地紧急操作入口。
- `kairo-platform-server` 已有 PostgreSQL/Flyway 权威状态、Redis/DB fencing sequence、规则版本、发布计划、
  Agent 命令、卸载执行、审计、RBAC、API 幂等记录和 desired/actual 规则链状态表。
- `kairo-platform-web`、`kairo-cli`、`kairo-sdk`、`kairo-mcp` 已共享 Platform API，不需要 V1.7 再建设新操作面。
- M0 已保存 V1.6 OpenAPI、错误码、配置、V1～V41 迁移和 Agent 协议基线，并建立破坏性变更测试。

### 2.2 必须正视的缺口

- `AgentCommandService`/`AgentCommandMapper` 有 attempts 和 lease，但 Agent ACK 尚未完整携带 dispatch epoch；
  旧 ACK 在重新派发后仍可能缺少可靠围栏。
- `PlatformCommandPoller` 的 `REFRESH_RUNTIME_STATE` 目前只返回 `{"refreshed": true}`，没有报告真实规则、
  revision、hash、TTL 或 degraded state。
- `RuleChainStateService` 能比较 desired/actual，却没有驱动自动收敛；目标 JVM 重启后内存规则会丢失。
- `BytecodeDiagnosticExchange`、`ScriptSessionExchange`、`TargetResolutionExchange` 有意只保存临时敏感数据；
  Platform 重启后不能安全恢复这些请求，必须失败得明确，不能假装持久化。
- `PlatformMaintenanceService` 当前会在 Agent 不可达时把部分计划直接写成 `UNLOADED/REMOVED`；Agent 断连不等于
  JVM 已卸载规则，该语义必须纠正。
- 默认部署是一个 Platform 进程。`RolloutExecutor` 的运行锁是本进程 `AtomicBoolean`，当前没有多节点 leader election。
- Platform 已引入 Actuator，但仍缺 Kairo 业务 readiness、低基数指标、统一 build identity 和可用支持包。
- 当前 Maven/Docker/运行时仍大量使用 `0.1.0-SNAPSHOT`，尚未形成一致的 `1.7.0` 发布物。
- 当前兼容 CI 存在 `continue-on-error`、失败探测和占位 job，不能作为正式支持证据。
- 根 Maven reactor 当前包含 18 个模块，但“模块、发行物、运行进程、产品应用”没有在实施文档中明确区分；
  `kairo-agent-core-modern` 和 `kairo-integration-tests` 等合理的无生产源码模块容易被误认为空应用，同时
  `kairo-object`、`kairo-sidecar` 确有边界弱化或遗留实现未被正式运行链路消费的问题。

任何实现若与以上事实冲突，应提交设计偏差，不得通过增加新模块、旁路状态或扩大基础设施来绕过。

### 2.3 应用、工具和代码模块审计

V1.7 在当前 `V1.7` 分支进行的源码审计得到以下事实。类数只用于发现异常，不作为机械合并依据：

| 类别 | 当前实现 | 审计结论 |
|---|---|---|
| 正式中心应用 | `kairo-platform-server`：110 个 main Java 文件；`kairo-platform-web`：约 95 个 TS/TSX/JS 文件 | 两个独立运行进程，分别拥有 Java/Spring 与 Node/Next.js 技术栈、故障域和发布边界，必须保留 |
| 嵌入式运行时 | `kairo-agent-core`：74 个 main Java 文件；`kairo-agent-server`：14 个、约 3,184 行；另有 bootstrap/assembly | Agent 位于目标 JVM，不是第三个中心微服务；ClassLoader、JDK 字节码版本和 shaded 发行边界必须保留 |
| Platform 客户端 | `kairo-sdk` 3 个类、`kairo-cli` 1 个类、`kairo-mcp` 2 个类 | 类少是薄适配器的预期结果；SDK 是公共库，CLI 与 MCP 的进程模型和调用协议不同，不因类少合并 |
| 本地高权限工具 | `kairo-attach-cli` 3 个类、`kairo-ops` 2 个类 | Attach 与 loopback 紧急恢复的权限不同，必须保持两个最小发行物，避免 ops 获得 attach 能力 |
| 内部库 | `kairo-api`、`kairo-bootstrap-api`、`kairo-groovy`、`kairo-core`、`kairo-object` | 前四个有契约/类加载/可替换后端边界；`kairo-object` 只有 4 个类且只有 Core/Agent 消费，没有独立发行或替换实现，边界不足 |
| 构建/验收模块 | `kairo-agent-core-modern` 0 个 main 类；`kairo-integration-tests` 0 个 main 类、6 个测试类 | 前者是 shaded assembly，后者是跨模块测试 source set；无 main 类是正确设计，不是空应用 |
| 非产品 fixture | `kairo-demo` 6 个类；`kairo-sidecar` 8 个类 | Demo 有意保持最小；sidecar 只服务 demo attach，其中 WAL/masking 代码没有生产消费者，不应维持产品模块假象 |

因此 V1.7 的目标不是把 18 个 Maven module 强行合成一个大单体，而是同时固定两种口径：

1. **正式产品应用固定为 2 个**：`Platform Server` 与 `Platform Web`。
2. **嵌入式产品运行时固定为 1 个**：`Runtime Agent`，随用户目标 JVM 运行，不计作中心应用。
3. CLI、MCP、SDK、Attach、Ops 是客户端/工具/库，不得在架构图或发布说明中伪装成平台微服务。
4. Demo、integration tests 和 shaded assembly 是 fixture/build boundary，不计作产品应用。
5. Java reactor 在 M1-G 只删除两个已证明错误的模块边界，从 **18 收敛到 16**；不得为了达到更小数字继续合并。

M1-G 的固定收敛决策是：

- 将 `kairo-object` 的源码和测试并入 `kairo-core`，保留现有 Java package，删除独立 Maven module；
- 将 `kairo-sidecar` 中真实使用的 attach executor 并入同权限域的 `kairo-attach-cli`，保留 demo attach
  的容器入口、环境变量和 HTTP 行为；删除没有生产消费者的 WAL/masking 实现及其孤立测试，删除独立 module；
- 保留 Platform Server/Web、Agent Core/Server/Bootstrap/Modern Assembly、SDK/CLI/MCP、Ops/Attach、
  Demo/Integration Tests 的现有边界；这些边界在 V1.7 不再重新讨论。

本节是 V1.7 对早期模块治理文档的更具体决策。发生冲突时以本节和 M1-G 为准；M1-G 完成时同步更新
`docs/architecture/module-boundary-governance.md`、README、构建脚本和 Compose，不允许长期保留两套说法。

## 3. V1.7 运行与支持边界

### 3.1 正式运行拓扑

V1.7.0 正式支持的控制面拓扑固定为：

```text
Browser / CLI / SDK / MCP
            |
     Platform Web
            |
  单个 Platform API + Scheduler 进程
        |                 |
  PostgreSQL 16       Redis 7（仅 fencing，按配置可选）
        |
Agent 主动注册、心跳、轮询命令
        |
目标 JVM
```

边界说明：

- PostgreSQL 是权威状态；Redis 丢失不得造成规则、发布和审计数据丢失。
- Redis 启用时不可用可以阻止需要新 fencing token 的写操作，但不应误杀 Platform liveness。
- 正式支持单个活跃 Platform 进程及其重启恢复；不承诺两个 Platform scheduler 同时主动运行。
- Agent 只能主动连接 Platform；Platform 不直连 Agent 暴露地址。
- Platform 不可用时，目标业务方法和已加载 Agent 继续运行；本地 `kairo-ops` 仍可执行紧急 disable/reset。
- “正式产品应用”只指 Platform Server 和 Platform Web；Agent 是嵌入式运行时，CLI/MCP/Attach/Ops 是工具，
  PostgreSQL/Redis 是基础设施，用户的目标 JVM 是被管理应用。发布、监控和故障统计必须使用这一口径。

### 3.2 候选支持矩阵

M3 必须用真实 CI 把候选矩阵冻结为最终矩阵。在证据形成前，候选声明如下：

| 组件/维度 | 候选正式支持 | 明确不承诺 |
|---|---|---|
| Platform | Linux x86_64，JDK 21，PostgreSQL 16，Redis 7 | Windows Platform、多节点 HA、多区域 |
| Platform Web | Linux 容器，Node 20 构建产物 | 浏览器插件或桌面客户端 |
| Agent 目标 JVM | JDK 17、21 | JDK 8、11 完整 Agent Core |
| 加载方式 | premain、agentmain、外部 attach | 绕过目标 OS/JDK attach 限制 |
| 目标形态 | 普通 Java、Spring Boot 3、父子同名 ClassLoader、JDK Proxy、CGLIB、Byte Buddy、Lambda、bridge/synthetic | 未经矩阵验证的框架/语言自动承诺 |
| OS | Linux x86_64 为主支持；macOS arm64/JDK 21 在真实 CI 通过后可正式支持 | Windows 在 V1.7.0 默认 `EXPERIMENTAL` |
| 数据库 | PostgreSQL 16 | MySQL、Oracle、SQL Server 生产运行 |

`kairo-agent-bootstrap` 和 `kairo-bootstrap-api` 是 Java 8 class file，不代表完整 Agent 支持 JDK 8；
`kairo-agent-core-modern` 和其他核心模块以 Java 17 为基线，Platform 明确以 Java 21 编译。V1.7 不为 JDK 8/11
再建设一套 Spring Boot 2/旧 Groovy/旧 Byte Buddy 核心发行物。

### 3.3 明确不做

V1.7 不允许夹带以下工作：

- 新增强位置、新规则链语义、新脚本档位或扩大脚本权限；
- 新 Web 业务页面、新 AI/MCP 工具、新公开产品资源族；
- 录制回放、数据集、Kafka、MinIO、审批流或实验编排；
- Kubernetes、Helm、Service Mesh、OIDC/SSO、Vault、云 KMS；
- 多 Platform 主动—主动、分布式 leader election、多区域容灾；
- JDK 8/11 legacy core、Spring Boot 2 专用发行线、Windows 全面适配；
- 为清理代码而进行全仓重命名、模块拆分、框架升级或控制器重写；唯一例外是 §2.3 和 M1-G 明确列出的
  两个删除式收敛，不得借 M1-G 重写业务代码；
- 以 `RESET_ALL` 代替精确恢复，或以修改测试断言代替修复产品缺陷；
- 只为“看起来像 LTS”而增加没有使用者、没有验收场景的基础设施。

出现上述需求时，记录到 V2 或独立兼容发行线，不阻塞 V1.7。

## 4. 不可违反的可靠性语义

### 4.1 PostgreSQL 权威性

- 正式规则、版本、desired state、发布计划、实例执行、命令状态、卸载状态和审计以 PostgreSQL 为准。
- 内存对象只能是缓存、等待器或临时敏感载荷，不能成为正式规则的唯一事实来源。
- 已提交的终态不能因进程重启回退；派生状态必须可从权威表重新计算。

### 4.2 命令语义

Agent 命令分为两类，分类是固定设计，不得由实现者随意改变。

#### DURABLE：允许安全恢复和重试

- `APPLY_RULE`
- `APPLY_CHAIN`
- `DISABLE_ALL`
- `ENABLE_ALL`
- `RESET_CLASS`
- `RESET_ALL`
- `STOP_AGENT`
- `REFRESH_RUNTIME_STATE`

DURABLE 命令的 payload 必须完整持久化；执行必须依赖 idempotency key、dispatch epoch、期望 revision/hash
中的适用字段。发生重试时，旧 owner 不能完成新 owner 的命令轮次。

#### TRANSIENT：进程重启后明确失败，不自动重放

- `START_RECORDING`、`STOP_RECORDING`
- `DISCOVER_TARGETS`、`LIST_LOADERS`、`LIST_CALL_SITES`、`RESOLVE_TARGET`
- 所有 `BYTECODE_*`
- 所有 `SCRIPT_*`

这类命令可能依赖内存中的脚本正文、class bytes、等待器或 JVM 瞬时观察。Platform 重启、等待器丢失或
deadline 到期后，命令进入机器可读失败态，由调用者重新发起。禁止为了“可恢复”而把脚本正文、敏感字节码或
大对象无边界写入数据库。

### 4.3 命令状态机

固定状态机：

```text
PENDING
  -> DISPATCHED(attempts=N, leaseExpiresAt=T)
      -> ACKED
      -> FAILED
      -> lease 过期且 attempts < maxAttempts -> DISPATCHED(attempts=N+1)
      -> lease 过期且 attempts >= maxAttempts -> FAILED(MAX_ATTEMPTS_EXHAUSTED)
```

规则：

- 同一轮 dispatch 只能有一个成功 claim。
- live lease 不可被抢占。
- Agent ACK 必须回显本轮 `attempts` 作为 `expectedAttempts`。
- V1.6 Agent 缺少 `expectedAttempts` 时，只允许 `attempts == 1` 的首次派发 ACK；重新派发后缺少 epoch 必须拒绝。
- ACKED/FAILED 是不可变终态；重复 ACK 返回同一结果或明确 conflict，不能再次推进 rollout/unload。
- `attempts >= maxAttempts` 的过期命令必须被终结，不能永久留在不可见的 DISPATCHED 状态。

### 4.4 desired/actual 收敛

- Platform desired state 只包含正式、仍有效的规则版本；临时试运行和已过期 TTL 规则不进入重启恢复集合。
- Agent actual state 必须来自真实运行时快照，不得由“命令曾 ACK”推测。
- `IN_SYNC`：revision 和 canonical hash 一致，不执行命令。
- `MISSING/BEHIND`：自动补发当前 desired state。
- `AHEAD/DIVERGED`：标记 degraded 并停止自动覆盖；用户通过既有重新发布或卸载操作处理。
- transformation hash 漂移必须遵循 V1.4/V1.5 的其他 Agent 共存和 `TARGET_DRIFTED` 语义，不能恢复最初 class bytes。

### 4.5 Agent 离线不等于已卸载

- 心跳租约过期只能把 Agent/实例标为离线或运行态未知。
- 不得仅因 Agent 不可达就把 operation plan 写成 `UNLOADED` 或把 runtime status 写成 `REMOVED`。
- 若同一 JVM 进程恢复连接，应先读取 actual state，再继续待处理卸载或对账。
- 若 `processStartId` 变化，说明是新 JVM 生命周期；旧内存增强自然消失，但正式 desired state 需要重新应用。
- 实例被长期清理时可以把执行历史标为 `ABANDONED`，但必须保留“未确认卸载”的历史事实。

### 4.6 失败边界

- 单个 JVM 内规则链应用继续使用现有原子快照和转换回滚。
- 多 JVM 发布不伪装成分布式事务；每个实例分别记录成功、失败、离线待补偿。
- 外部不可事务副作用维持 at-least-once 边界，并通过 idempotency/fencing 降低重复影响。
- Platform 不可用不能把异常传播到目标业务方法；Agent 运行时继续 fail-open。

## 5. 证据模型

### 5.1 门禁级别

同一 requirement 必须分别记录三个门禁，禁止用一次本地测试宣称整个 requirement 已完成：

```text
PR       代码与短程回归门禁
RC       固定 CI/受控环境候选版门禁
RELEASE  最终发布、长稳、签名和人工批准门禁
```

每个门禁状态只能是：

- `PASSED`
- `FAILED`
- `SKIPPED`
- `NOT_RUN`
- `EXPERIMENTAL`

`SKIPPED/NOT_RUN/EXPERIMENTAL` 不能成为正式支持或最终发布证据。

### 5.2 acceptance manifest v2

`v1.7-acceptance-manifest.json` 在首次记录 M1 证据前升级为 schema `2.0`。最低结构：

```json
{
  "schemaVersion": "2.0",
  "release": "V1.7.0",
  "buildId": "<git commit>",
  "requirements": [
    {
      "id": "V17-RECOVERY",
      "gates": {
        "PR": {
          "status": "PASSED",
          "environment": {},
          "commands": [],
          "reports": [],
          "startedAt": "...",
          "endedAt": "...",
          "limitations": []
        },
        "RC": { "status": "NOT_RUN" },
        "RELEASE": { "status": "NOT_RUN" }
      }
    }
  ]
}
```

M0 已存在的 schema 1.0 证据保留其历史事实；迁移到 v2 时只重排结构，不得把尚未执行的 RC/RELEASE
门禁补写为 `PASSED`。

### 5.3 固定证据文件

| 文件 | 责任里程碑 | 含义 |
|---|---|---|

### 8.1 M1-A：命令 lease、epoch 与终态安全

#### 目标

建立可证明的 Agent command claim/ack 状态机，消除重复 claim、live lease 抢占、旧 owner ACK、终态覆盖和
最大尝试耗尽后永久卡住的问题。

#### 允许修改

- `kairo-platform-server/.../command/AgentCommandService.java`
- `kairo-platform-server/.../persistence/mapper/AgentCommandMapper.java`
- `kairo-platform-server/src/main/resources/mapper/AgentCommandMapper.xml`
- `kairo-agent-server/.../PlatformCommandPoller.java`
- 必要的共享可选协议常量/DTO；
- M1-A 专项测试和小型 fixture。

#### 禁止修改

- 历史 Flyway SQL；
- rollout/unload 业务语义；
- Web、CLI、MCP；
- 规则链实现、脚本引擎、字节码转换实现；
- 通过提高 sleep/timeout 掩盖竞态。

#### 必须实现

1. `dispatchCommand` 使用原子条件更新：PENDING 可 claim；DISPATCHED 只有 lease 已过期才能重新 claim。
2. 每次成功 dispatch 后 `attempts + 1`，响应中返回该值。
3. Agent 所有 ACK 路径都回传 `expectedAttempts`，包括成功、capability failure 和异常失败。
4. ACK SQL 同时校验 `status=DISPATCHED` 与 dispatch epoch。
5. Legacy V1.6 ACK 未携带 epoch 时只允许 `attempts=1`；`attempts>1` 必须返回 `AGENT_COMMAND_STATE_CONFLICT`。
6. 重复/延迟 ACK 不再次执行 rollout/unload/审计推进。
7. lease 过期且 `attempts>=maxAttempts` 的命令原子终结为 FAILED，错误码固定为
   `AGENT_COMMAND_MAX_ATTEMPTS_EXHAUSTED`。
8. 全部时间由可注入 `Clock` 控制；并发测试使用 barrier/latch，不使用长 sleep。

#### 必须新增或等价测试

- `AgentCommandLeaseIntegrationTest`
- `AgentCommandAckFencingIntegrationTest`
- `AgentCommandPollerEpochTest`

覆盖：

- 两个 claim 并发只有一个成功；
- live lease 不可抢；
- expired lease 只有一个接管者；
- 当前 epoch ACK 成功；
- stale epoch、未来 epoch 和缺失 epoch 的重新派发 ACK 被拒绝；
- legacy 首次派发 ACK 仍成功；
- ACKED/FAILED 终态不变；
- maxAttempts 耗尽后进入明确 FAILED。

```bash

  test -Dtest='AgentCommand*Test,PlatformCommandPollerEpochTest' \

mvn -B -ntp -pl kairo-platform-server,kairo-agent-server -am test
git diff --check
```

#### 完成条件

专项测试和两个模块全量测试通过；Agent 实际回传 epoch；没有未终结的 maxAttempts 命令；没有改动 M1-A
允许范围以外的产品语义。

#### 目标

### 8.4 M1-D：注册、重连和 JVM 重启对账

#### 目标

#### 允许修改

### 8.7 M1-G：应用口径与模块边界收敛

## 9. M2：性能、状态循环和资源泄漏

M2 的任务是测量现有系统并修复被证据证明的缺陷，不是重新设计 Agent。

### 9.1 M2-A：基线 harness 与预算

#### 允许修改

- 新增独立 benchmark/soak harness，可放在 `kairo-integration-tests` 的专用 source set 或新增仅测试模块；
- 必要的只读计数器和测试钩子；
- 被真实基准证明的局部性能缺陷。

#### 禁止修改

- 仅为跑分改变规则语义或安全默认值；
- 在普通 JUnit 中用单次 `System.nanoTime()` 作为跨机器硬 SLO；
- 引入生产必需的 profiler/APM；
- 在业务热路径增加网络或数据库调用。

#### 测量场景

- 无 Agent 基线；
- Agent 已加载但目标未增强；
- 目标已增强但规则未命中；
- BEFORE/RETURN/THROWS 命中；
- Groovy no-op/参数读取/返回替换；
- 1、5、20 条规则链；
- 大量已加载类和规则的查询；
- 事件缓冲区满载、丢弃和背压。

#### 采样规则

- 固定 runner/JDK/JVM 参数；
- 预热、至少 5 个 fork 或等价隔离进程、每个场景保存原始样本；
- 输出 median/P95/P99、误差和环境；
- V1.6 与 V1.7 在同一 runner 依次执行；
- 初始相对预算：关键未命中/命中场景的 median/P95 不得比 V1.6 退化超过 20%；超过时必须分析，
  不能简单提高阈值；
- 首次有效基线写入小型 `v1.7-performance-budget.json`，后续调整必须经过文档评审。

### 9.2 M2-B：10,000 次真实状态循环

每个 cycle 必须真实执行：

1. 增强目标类；
2. 调用目标方法并验证行为；
3. 更新或局部卸载规则；
4. 再次调用验证；
5. 完全卸载；
6. 验证方法行为和规范化字节码 hash 回到正确基线。

覆盖普通方法、构造器、调用点、规则链、父子 ClassLoader 同名类以及一次并发冲突场景。禁止 sleep-only、
只修改内存模型或只验证 registry 数量。

### 9.3 M2-C：ClassLoader/Groovy 泄漏

覆盖：

- 可卸载业务 ClassLoader；
- Groovy 脚本 ClassLoader 和 compile cache；
- JDK Proxy、CGLIB、Byte Buddy 生成类；
- Lambda、bridge/synthetic；
- 字节码 snapshot、journal、method cache、rule registry 和统计缓存。

短程 PR 门禁：100～500 cycle。RC 门禁：10,000 cycle 和 2 小时 soak。观测：heap、Metaspace、线程、
live ClassLoader weak reference、已加载类和文件描述符（平台支持时）。

初始判定预算：

- 所有显式创建的可卸载 ClassLoader 在最终强引用分析后最多残留 2 个；
- 运行线程数相对稳定窗口增长不超过 2；
- 文件描述符相对稳定窗口增长不超过 5；
- 最后一个稳定窗口的 full-GC 后 heap 不高于首个稳定窗口 15%；
- Metaspace 不高于首个稳定窗口 10%；
- snapshot/cache/rule 计数在完全卸载后回到预算内。

如果平台、GC 或测试噪声证明某数字不适用，必须先提交包含原始样本的预算调整，不允许测试自行放宽。

### 9.4 M2-D：长稳 harness

- 每分钟采集时间序列摘要；
- 持续执行真实调用，每 5 分钟执行一批增强/更新/卸载，每 30 分钟执行 Agent/Platform 断连恢复；
- RC 固定运行 2 小时；最终 RELEASE 固定运行 7 天；
- 失败条件：进程异常退出、OOME、业务异常泄漏、永久状态漂移超过 5 分钟、资源持续超过预算、无法完成精确卸载；
- 输出 `soak-result.json`，包含 build ID、JDK/JVM 参数、周期数、失败时间、最后状态和原始时间序列 URI。

### 9.5 M2 固定脚本接口

M2 必须交付以下仓库脚本接口，后续 CI 和 M6 只能调用这些接口，不再各写一套临时命令：

```bash

./scripts/v1.7/run-performance.sh \
  --mode pr --baseline V1.6.0 --candidate HEAD \
  --output target/v1.7

# 真实增强/调用/局部卸载/完全卸载循环
./scripts/v1.7/run-state-cycle.sh \
  --cycles 500 --output target/v1.7

# ClassLoader、Groovy、proxy/Lambda 泄漏短程
./scripts/v1.7/run-leak-check.sh \
  --cycles 500 --output target/v1.7

# RC 使用 --duration PT2H；M6 使用 --duration P7D
./scripts/v1.7/run-soak.sh \
  --duration PT2H --output target/v1.7

# 只验证 schema、build ID、预算和退出状态，不重新跑测试
```

脚本必须：非零退出表示门禁失败；支持 `--help`；记录完整命令、环境和 build ID；不自动修改预算或验收 manifest；
不下载未锁定版本的工具。脚本内部可以调用 Maven/Java harness，但不能以 shell sleep 模拟增强循环。

### 9.6 M2 完成条件

- `V17-PERF.PR` 和短程 `V17-SOAK.PR` 通过；
- 10,000 cycle、2 小时 soak 属于 RC 门禁；
- 7 天 soak 只在 M6 标记 RELEASE；
- 性能或泄漏失败若暴露产品缺陷，使用 `bugfix/v1.7-<scope>` 最小修复，不进行无证据重构。

#### 10.4.1 M3-A：矩阵契约、行级证据与聚合基础

#### 10.4.2 M3-B：普通 Java 的 premain、external attach 与 macOS 行

验收：目标平台上的承诺行真实通过；错误 JDK/OS/加载模式、未产生独立 PID、只编译未执行均 fail closed；
普通 Maven CI 不受影响。

#### 10.4.3 M3-C：Spring Boot 3 可执行包

范围仅限 C03、C04：建立一个最小、受控的 Spring Boot 3 executable-jar fixture，在 Linux x86_64/JDK 21
分别验证 premain 和 external attach 的注册、发布、真实调用和精确卸载。fixture 必须作为独立 JVM 运行，
不得用测试 JVM 内直接构造 Spring 类替代，不扩展到 Spring Boot 2 或独立 Tomcat。

验收：C03、C04 行级证据通过；证据包含可执行 jar、独立 PID、加载模式与完整行为断言；普通 jar、错误
loader 或未实际调用目标方法的伪证据被拒绝。

#### 10.4.4 M3-D：ClassLoader、代理、Lambda/bridge/synthetic

范围仅限 C05、C06、C07：

- C05 使用 parent/child 同名类 fixture，证明只增强指定 loader，另一个 loader 行为和字节码不变；
- C06 固定覆盖 JDK Proxy、CGLIB、Byte Buddy 三种仓库内 fixture，验证目标解析、真实调用和精确卸载；
- C07 在 JDK 17、21 覆盖 Lambda、bridge、synthetic 的发现策略与实际增强/卸载行为；
- 所有场景都在独立目标 JVM 运行并输出 M3-A 行级证据。

禁止：泛化为所有框架代理、Kotlin 协程、任意第三方生成器兼容承诺，或为通过测试放宽目标唯一性。

验收：C05～C07 的每个固定子场景均真实执行且通过；loader 误伤、只做类型探测、只打印 warning、

#### 10.4.5 M3-E：redefine/retransform 漂移与受控 Agent 共存

范围仅限 C08、C10：

- C08 在独立 JVM 中执行真实 redefine、retransform 和 hot update；能够安全对账时继续，不能安全对账时
  必须精确落为 `TARGET_DRIFTED`，不得静默覆盖；
- C10 只使用仓库内一个固定 Byte Buddy Agent fixture，验证 Kairo 增强/更新/卸载不移除或破坏对方变换；
- 若真实证据暴露产品缺陷，停止本包并按 `bugfix/v1.7-<scope>` 最小修复，不能在矩阵工作包中顺手重构
  产品热路径。

验收：C08、C10 行级证据通过；基线/变换 hash、执行顺序、卸载后行为均可核对；用 mock Instrumentation、
仅比较内存对象或把漂移强行 RESET 的测试不计入验收。

#### 10.4.6 M3-F：权威 CI、聚合结果与兼容性文档

范围：

- 将 `.github/workflows/compatibility-matrix.yml` 收敛为唯一正式矩阵 workflow，逐行调用 M3-A 固定接口；

## 11. M4：最低限度可运维性

### 11.1 health 语义

必须提供：

- `/actuator/health/liveness`：只反映进程是否能继续服务；DB/Redis/Agent 离线不能让 liveness DOWN。
- `/actuator/health/readiness`：DB、Flyway validate 和配置为必需的 Redis 正常时 UP。
- `/actuator/info`：version、git commit、build time、Java target、contract baseline。

测试必须真实断开并恢复 DB/Redis，验证 HTTP status、body 和恢复，不允许 mock 一个固定 DOWN indicator 代替。

### 11.2 固定业务指标

以下名称作为 V1.7 运维契约；实现使用 Micrometer，标签只能来自本文列出的有限集合：

| 指标 | 类型 | 允许标签 |
|---|---|---|
| `kairo_agent_online` | gauge | `status` |
| `kairo_agent_command_backlog` | gauge | `status`, `command_type` |
| `kairo_agent_command_total` | counter | `command_type`, `result` |
| `kairo_operation_total` | counter | `operation_type`, `result` |
| `kairo_operation_duration_seconds` | timer | `operation_type`, `result` |
| `kairo_runtime_rule_targets` | gauge | `state` |
| `kairo_reconcile_total` | counter | `result` |
| `kairo_rollback_total` | counter | `result` |
| `kairo_ttl_cleanup_total` | counter | `result` |
| `kairo_platform_build_info` | gauge=1 | `version`, `commit` |

禁止使用 ruleId、agentId、instanceId、className、methodName、traceId、用户名等无界 label。需要定位具体对象时使用
结构化日志和现有资源查询。

### 11.3 支持包

不新增复杂 Web 页面。复用现有 CLI 边界：

- `kairo-cli diagnose --output <zip>` 收集 Platform health/info、指标名和必要值、版本、最近操作摘要；

实现若发现现有 CLI 无法复用，可以增加内部只读 endpoint，但不得创建新的业务资源族或浏览器功能。

### 11.4 runbook

最低文档：

- Platform 启动失败/Flyway 失败；
- PostgreSQL/Redis 不可用；
- Agent 离线或命令积压；
- 发布卡住、部分失败和状态漂移；
- 卸载失败和离线待补偿；
- TTL 未清理；
- heap/Metaspace/ClassLoader 持续增长；
- Platform 不可用时使用 `kairo-ops` 紧急恢复；
- 1.6 → 1.7 升级和应用回退保护。

文档命令必须在 CI 或演练中执行；告警必须引用上表真实指标，不添加不存在的指标名。

## 13. M6：LTS 候选与最终认证

M6 是发布活动，不是继续扩展产品的开发里程碑。

### 13.1 进入条件

### 13.2 两阶段工作包

M6 只保留两个工作包。下面列出的演练、矩阵、长稳和发布动作是工作包内的验收清单，不再拆成
M6-C～M6-F，也不为每项演练建立独立开发阶段。

#### 13.2.1 M6-A：RC 综合认证

1. 固定候选 commit，后续只接受阻断缺陷修复。
2. 在 Linux/JDK 21/PostgreSQL 16/Redis 7 上执行 1.6 → 1.7 升级、备份恢复和应用回退保护演练。

#### 13.2.2 M6-B：LTS 最终认证与发布

1. 对通过 M6-A 的同一候选 commit 执行固定 7 天 soak；候选 commit 发生变化时，按缺陷风险重新执行受影响长稳门禁。
2. 从干净 checkout 构建最终 artifact，生成最终 SBOM、漏洞/许可证报告、hash、cosign 签名和 provenance。
3. 由独立验收者按 release manifest 复现全部适用 RELEASE 门禁。
4. 生成最终支持矩阵、已知限制、升级/备份/恢复说明，填写 LTS 日期、责任方和批准信息。
5. 只有全部 RELEASE 门禁通过后，才执行 §13.4 的发布和认证动作。

M6-B 是一个连续的发布工作包；7 天 soak、最终供应链、独立验收和发布动作是同一阶段内的顺序门禁，

## 15. Claude Code 执行协议

本节是给开发智能体的强制执行边界。

### 15.1 一次只做一个工作包

### 15.2 开工步骤

1. 读取本文、当前 `git status`、`git diff` 和该工作包允许修改的文件。
2. 保留所有现有未提交工作；不得 reset、checkout 或覆盖其他智能体修改。
3. 列出当前代码与工作包验收条目的映射。
4. 只实现缺失条目；已有正确实现不重写。
5. 若必须修改允许范围外的产品模块，停止编码并提交设计偏差说明。

### 15.3 实现约束

- 不新增同义状态、同义 DTO、第二套 registry 或旁路数据库表。
- 不引入本文未批准的基础设施、中间件、框架或运行时依赖。
- 不改变 V1.6 业务语义和 M0 基线；协议只能 additive。
- 不为了“代码优雅”进行大范围重构。
- 优先复用现有 `Clock`、revision/hash、idempotency、fencing、audit 和 PlatformException。
- 遇到不确定状态时 fail closed 到可诊断状态，不假报成功。
- 不 commit，由 Codex 审查、验收和提交。

### 15.4 交付格式

Claude 完成后必须输出：

```text

风险：仍可能失败的边界
建议主验收步骤：精确命令
```

### 15.5 强制停止条件

出现以下任一情况，Claude 必须停止扩大实现并报告：

- 需要改变本文可靠性语义；
- 需要修改 V1～V41 迁移；

- 只能通过降低测试质量才能继续。

主验收者决定修改方案、建立 bugfix 分支或退回前一工作包。开发智能体不得自行扩大范围。
