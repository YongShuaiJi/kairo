# V1.7 技术改造方案：LTS 稳定性验证与最终封版

> 上游基线：`V1.6.0`（commit `113823b`，V1.6 验收时 Maven 573 tests 全绿）。
> 开发分支：`V1.7`；最终版本：`V1.7.0`；维护版本：`V1.7.x`。
> 方案状态：**架构评审冻结**。实现若要改变范围或验收门槛，必须先修改本方案并说明原因。
> 版本性质：稳定、兼容、可运维、可升级的 LTS 封版；不新增方法增强产品能力。
> 路线图：[V1.X 版本路线图 §9](../v1.x-version-roadmap.md)。

## 1. 版本结论与边界

V1.7 的任务不是继续堆功能，而是把 V1.1～V1.6 已有能力变成可以长期发布和维护的产品。
V1.7.0 发布后，V1.X 功能开发结束；后续 V1.7.x 只做 LTS 维护。

### 1.1 必须交付

1. 冻结 API V1、错误码、配置、数据库历史迁移和 Agent 协议，并建立破坏性变更门禁。
2. 验证升级、备份、恢复、重启、断连、重试、乱序、回滚和状态对账。
3. 建立性能基线、并发压力、重复增强/卸载和 ClassLoader/脚本泄漏测试。
4. 用实际 CI 结果冻结 JDK、操作系统、框架、附加方式和新旧组件组合的支持矩阵。
5. 交付正确的存活/就绪探针、低基数指标、脱敏诊断包、告警和故障处置手册。
6. 交付可追溯发布物：版本清单、校验和、SBOM、安全报告、签名和 provenance。
7. 定义可执行的 LTS 生命周期、缺陷等级、弃用、回补和发布规则。
8. 为每条发布结论保存机器可读证据，未执行的场景不得写成通过。

### 1.2 不做

- 不新增增强位置、脚本权限等级、规则链语义、API 产品能力、Web 功能或 AI/MCP 工具。
- 不借“稳定性改造”改变 V1.6 的业务语义、默认权限、错误码含义或审计边界。
- 不在 V1.7 引入录制回放、数据集、分布式实验编排等 V2.0 产品域。
- 不为满足指标而跳过、放宽或伪造测试；不能稳定自动化的项目必须作为人工发布门禁记录证据。

### 1.3 进入条件

- Git 基线必须可追溯到 annotated tag `V1.6.0` / commit `113823b`。
- V1.6 完整后端、前端和真实 Agent 插桩验收已通过。
- V1.7 开始时先保存 V1.6 契约快照；保存后才允许稳定性改造。

## 2. 支持声明与证据原则

支持矩阵不是愿望清单。每个组合只能处于以下一种状态：

| 状态 | 含义 | 能否写入“正式支持” |
|---|---|---|
| `PASSED` | 在对应真实环境执行指定测试，证据已归档 | 可以 |
| `FAILED` | 已执行但失败 | 不可以，且若属于承诺矩阵则阻断发布 |
| `SKIPPED` | 环境不具备或前置条件不满足，并记录原因 | 不可以 |
| `NOT_RUN` | 没有执行证据 | 不可以 |
| `EXPERIMENTAL` | 有局部证据但未达到完整门槛 | 只能声明实验性 |

本地环境目前只能提供 macOS arm64 / JDK 21 的证据。Linux、Windows、其他 JDK 和签名等
结论必须来自 CI 或受控发布环境。`continue-on-error`、只编译、只探测版本、模拟 OS 名称都不算通过。

## 3. 冻结契约（W0，最高优先级）

### 3.1 API V1 与错误码

保存规范化 OpenAPI 快照，不只保存 path 列表。兼容比较至少覆盖：

- path、HTTP method、认证/权限要求、content type、必填参数和参数位置；
- request/response schema、required、nullable、enum、格式和成功/错误状态码；
- 分页、幂等键、操作状态、错误响应结构及公开错误码含义；
- deprecated、replacement 和最早移除大版本。

允许不破坏旧客户端的追加变化；删除 operation/字段、增加必填项、收窄 enum、改变类型、复用错误码、
提升权限要求或改变既有成功语义均阻断构建。快照更新必须由显式命令完成，并在变更说明中分类为
`additive` 或 `breaking`；V1.7.x 禁止接受 `breaking`。

门禁：`ApiV1FreezeTest` + 规范化 schema diff；既有 `OpenApiContractTest` 和
`ResourceFamilyCompatTest` 继续保留。禁止仅通过控制器反射推断完整契约。

### 3.2 数据库迁移

- 冻结 V1～V41 已发布 SQL 的文件名、version、SHA-256 和 Flyway checksum；不得修改、删除或重排。
- 新结构只能追加迁移，且必须通过空库迁移、V1.0/V1.1…V1.6 代表性快照升级、重复启动和 Flyway
  `validate`。
- 迁移失败必须保持可诊断状态；数据库“回滚”采用升级前备份/恢复，不承诺危险的 down migration。
- 测试 fixture 必须来自对应历史版本生成或经过校验，禁止手写一个与历史无关的伪快照。

门禁：`MigrationFreezeTest`、`MigrationForwardCompatTest`、`MigrationBackupRestoreTest`。

### 3.3 配置

冻结公开的 `kairo.*`、`management.*` Kairo 覆盖项及 `KAIRO_*` 环境变量：键名、类型、默认值、
是否敏感、适用组件和弃用信息。删除、改名、改变类型/安全默认值或让旧值失效属于破坏性变更。
敏感配置不得进入日志、诊断包或 build manifest。新增配置必须有默认值、文档和配置绑定测试。

门禁：`ConfigFreezeTest` 使用结构化绑定元数据和显式清单；禁止只用正则扫描源码作为唯一事实来源。

### 3.4 Agent 协议与组件组合

冻结 protocol version、消息 envelope、命令/响应 schema、capability、错误和幂等/顺序字段。
新增命令并不天然兼容：只有旧 Agent 会忽略未知 capability、平台在协商前不发送未知命令，且组合测试通过，
才可判定为 additive。无法协商的组合必须在执行前拒绝并返回机器可读原因，不能连接后随机失败。

至少验证：

- V1.7 Platform ↔ V1.6 Agent；
- V1.6 Platform ↔ V1.7 Agent；
- V1.7 ↔ V1.7；
- 不支持的协议版本和 capability 拒绝路径。

门禁：`AgentProtocolFreezeTest`、`AgentProtocolNegotiationTest` 和跨版本 fixture 测试。

## 4. 可靠性、升级与恢复（W1）

所有测试断言 DB 行、协议响应、Agent 快照、revision/hash 和目标方法实际行为，不能只断言日志。

| 场景 | 必须证明的结果 |
|---|---|
| Platform 重启 | 已提交状态保留；过期 lease 可接管；不会重复应用已完成操作 |
| DB/Redis 短时不可用 | readiness DOWN；存活不受依赖故障误杀；恢复后积压命令按幂等语义处理 |
| Agent 断连/重连 | 业务方法继续；重连后 desired/actual state 对账；旧命令不能覆盖新 revision |
| 发布/卸载中 Agent 退出 | 操作进入明确可恢复状态；重试后全成或维持旧状态，不留半增强状态 |
| 命令重复、延迟、乱序 | 围栏、版本和幂等键共同阻止旧结果覆盖新状态 |
| JVM 重启 | 运行态丢失后按平台期望重新应用；TTL 到期规则不得复活 |
| 多目标失败 | 转换前校验；失败时回滚已修改目标，或明确进入可重试失败态 |
| 紧急停止 | 在控制面可用/不可用的既定边界内均有确定行为和审计记录 |
| 升级 | 历史 DB/配置/规则可以升级到 V1.7，API 和协议保持兼容 |
| 回退 | 应用回退前先判定 DB 兼容；不兼容时阻止启动并指向备份恢复流程 |

恢复测试必须包含真实时钟可控方案或合理超时，避免依赖长时间 `sleep`。外部 HTTP 等不可事务副作用仍按
V1.6 的 at-least-once 边界公开说明。

## 5. 性能、压力与长稳（W2）

### 5.1 先建基线，再冻结预算

不能在普通 JUnit 中用墙钟纳秒数作为跨机器硬 SLO。分为两类：

- PR 回归门禁：功能正确性、资源计数不漂移、相对 V1.6 同机基线无显著退化；使用预热、重复采样、
  中位数/分位数和容差，失败时保存原始样本。
- 候选版性能门禁：在固定 runner/JDK/CPU 参数上执行 JMH 或等价独立 harness，生成 JSON 报告并与
  已批准 V1.6 基线比较。绝对 SLO 在首次稳定测量后冻结，不凭空编写数字。

测量：Agent 空载 CPU/heap/Metaspace/thread；增强未命中；命中与脚本；多规则链；大量类/规则查询；
事件缓冲区满载、丢弃和背压。

### 5.2 并发与状态循环

- 不少于 10,000 次真实增强、重新增强、局部卸载、完全卸载循环；最终行为和字节码 hash 与预期一致。
- 重叠与不重叠目标并发操作，覆盖同优先级排序、快照冻结、取消、失败回滚和卸载。
- harness 每个 cycle 必须执行真实 transform 和目标调用；禁止 sleep-only 或只修改内存模型。

### 5.3 泄漏验证

覆盖普通类、可卸载 ClassLoader、Groovy 脚本 ClassLoader、代理/Lambda 和规则缓存。采集 heap、
Metaspace、线程、已加载类、ClassLoader 弱引用、文件描述符（平台支持时）及 GC 后趋势。

`System.gc()` 只能协助观测，不能以单次未回收直接判失败。判定使用预热后的多窗口趋势、最终强引用分析和
机器可读预算。PR 运行短程测试；RC 在固定环境运行至少 10,000 cycle；7～14 天 soak 作为正式发布门禁，
需保存时间序列、JVM 参数、构建 ID 和退出原因。未完成长期 soak 不得发布 LTS。

## 6. 兼容矩阵（W3）

### 6.1 分离构建 JDK 与目标 JVM

当前 reactor 使用 Java 17 / Spring Boot 3.3，不能宣称整个系统可在 JDK 8/11 编译运行。
矩阵必须区分：

- Platform/CLI/MCP 的运行 JDK：按实际构建和启动结果冻结；
- Agent artifact 的 class-file target；
- 被注入目标 JVM 的 JDK：8/11/17/21 分别用真实目标进程做 attach/premain、增强、调用、卸载；
- 测试编译 JDK：只表示构建环境，不等于目标 JVM 支持。

如果要正式支持 JDK 8/11 目标 JVM，必须产出可在该 JVM 加载的 Agent/Bootstrap artifact，不能用
JDK 17 编译失败后 `continue-on-error` 代替。若 V1.7 无法完成，JDK 8/11 必须降级为未支持，并记录
与原 V1.5 目标的差距，不能封版时虚报。

### 6.2 维度与证据

- OS：Linux、macOS、Windows；
- 目标 JVM：8、11、17、21；
- attach：premain、agentmain、外部 attach；
- 框架/ClassLoader：普通、Spring Boot 2/3、Tomcat、父子同名、可卸载 loader；
- 动态形态：JDK proxy、CGLIB/Spring AOP、Byte Buddy、Lambda、bridge/synthetic；
- 共存：项目承诺的其他 Agent 组合。

不要求笛卡尔积全部执行，但必须定义有风险依据的最小组合覆盖，每个正式支持维度至少在一个真实端到端组合
中通过。CI 上传 `compatibility-result.json` 和测试报告；汇总任务发现承诺组合为 `FAILED/SKIPPED/NOT_RUN`
时必须失败。Windows/macOS 不能只做能力探测。

## 7. 运维就绪（W4）

### 7.1 探针

- liveness 只表示进程自身可继续服务，不能因 DB/Redis/Agent 离线而 DOWN，避免重启风暴。
- readiness 表示能否接受需要依赖的请求，应检查 DB、必要迁移状态及被配置为必需的 Redis。
- 可选依赖降级必须展示组件状态，但不得错误阻断整个实例。
- 测试真实注入依赖故障与恢复，验证 HTTP 状态、health body 和恢复时间。

### 7.2 指标、日志和诊断包

指标至少覆盖操作延迟/结果、命令积压、Agent 在线/漂移、增强目标数、回滚、TTL 清理和错误分类。
标签只能使用稳定低基数字段；禁止 ruleId、traceId、类名等无界标签。日志和审计必须携带 build/version、
operationId 等关联字段。

诊断包包含 build manifest、配置键（值脱敏）、health、指标快照、线程栈、内存摘要、最近操作和 Agent 摘要；
默认不收集脚本正文、Token、密码、Authorization、环境变量密值或完整 heap dump。测试必须植入 canary secret，
再断言 zip 文件名和内容均不包含 secret，并限制文件大小和采集超时。

### 7.3 SLO、告警和 runbook

SLO 分为产品目标和发布测量值，二者不可混写。告警必须引用真实存在的指标并说明 `for`、severity、影响和
恢复条件。runbook 至少覆盖 Platform/DB/Redis 故障、Agent 断连、发布卡住、卸载失败、状态漂移、TTL 未清理、
资源持续增长、升级失败和紧急停止。文档门禁校验链接、命令、指标名和必要章节，不用脆弱的全文关键字充数。

## 8. 发布与供应链（W5）

### 8.1 确定性与可追溯性

- 统一项目版本为 `1.7.0` 候选版本，禁止发布物继续显示 `0.1.0-SNAPSHOT`。
- manifest 包含 version、git commit、source tag、构建 JDK、target、构建时间和契约基线版本。
- 所有发布 artifact 生成 SHA-256；相同源码/工具链的两次隔离构建应字节一致。若某类产物不能复现，必须
  记录具体非确定字段并在发布前修复，不能只固定一个 timestamp 就宣称可复现。
- `/actuator/info`、CLI `--version`、Agent 握手和诊断包报告同一 build identity。

### 8.2 SBOM、安全、许可证、签名和 provenance

- 为最终分发包生成 CycloneDX SBOM，包含传递依赖；依赖/许可证政策使用允许、禁止和有期限的例外清单。
- 漏洞扫描报告必须对应最终 SBOM；Critical/High 未修复或没有批准且到期日明确的例外时阻断发布。
- GPG/Sigstore 等签名在受控发布环境执行；无密钥可以让本地测试 SKIP，但正式发布缺签名必须失败。
- provenance 的 subject hash 必须与最终 artifact 一致，materials 指向源码 commit 和依赖锁定信息。
- 发布流程生成 release manifest，集中记录 artifact、hash、signature、SBOM、provenance 和各门禁证据 URI。

不得把“profile 已配置”当作扫描/签名已经完成。

## 9. LTS 维护规则（W6）

权威规则见 [V1.7 LTS 支持、弃用与回补策略](./v1.7-lts-policy.md)。代码门禁只验证机器可验证的契约；
是否应回补、风险分级和例外批准属于发布治理，不用读取 Markdown 关键字的伪测试代替评审。

## 10. 实施里程碑与顺序

V1.7 仍使用一个开发分支，但按以下里程碑推进。后一个里程碑不能掩盖前一个的失败。

1. **M0 基线冻结**：W0 快照、规范化工具、破坏性变更测试和证据格式。
2. **M1 可恢复**：W1 升级/备份/恢复/断连/乱序/回滚测试。
3. **M2 可测量**：W2 性能基线、压力、泄漏和 soak harness；先采样后冻结预算。
4. **M3 可兼容**：W3 拆分 Agent/Platform JDK 目标，建立真实 OS/JDK/框架矩阵和汇总门禁。
5. **M4 可运维**：W4 探针、指标、脱敏诊断包、告警和 runbook。
6. **M5 可发布**：W5 版本统一、可复现构建、SBOM、安全、签名、provenance、升级演练。
7. **M6 LTS 候选**：冻结策略和已知限制，执行 RC 门禁、长期 soak 和独立验收。

实现过程中发现 V1.6 缺陷，使用 `bugfix/v1.7-<scope>` 分支修复并回归，再合并回 `V1.7`；不得绕过
冻结门禁直接修改契约基线。

## 11. 分层验收门禁

### 11.1 PR 必跑门禁（每次变更）

- 契约、迁移、配置、协议冻结测试；
- Maven 全 reactor 测试和真实 Agent 短程插桩/卸载测试；
- Web lint、typecheck、vitest、production build；
- 短程并发/状态循环和泄漏回归；
- 诊断包脱敏、安全静态门禁、SBOM schema 与依赖政策；
- Linux/JDK 17、21 的主构建与目标 JVM 测试。

### 11.2 RC 必跑门禁（每个候选版）

- 承诺的 OS/JDK/attach/框架/组件组合全部有 `PASSED` 证据；
- 从每个可获得的 V1.X 数据快照升级到 RC，并执行备份恢复演练；
- 固定 runner 性能对比、10,000 次状态循环、并发压力及泄漏预算通过；
- 两次隔离构建产物一致，最终 SBOM/安全/许可证报告通过；
- 安装、升级、回退、紧急停止和灾难恢复 runbook 实际演练。

### 11.3 V1.7.0 发布门禁

- 7～14 天 soak 完成且无持续 heap/Metaspace/thread/ClassLoader/file-handle 增长；
- 所有 P0/P1 缺陷清零；P2 有 owner、规避方式和目标版本；
- Critical/High 漏洞清零或存在书面批准、影响分析和未过期例外；
- 最终 artifact 已生成并验证 hash、signature、SBOM 和 provenance；
- 支持矩阵、已知限制、升级/备份/恢复文档与实际证据一致；
- 独立验收从干净 checkout 复现所有适用门禁。

任何一项 `FAILED`、承诺项 `SKIPPED/NOT_RUN` 或证据缺失均阻断 LTS 发布。

## 12. 验收证据矩阵

仓库应维护机器可读 `v1.7-acceptance-manifest.json`，每项至少包含：requirement ID、门禁级别、
代码/测试、执行命令、环境、build ID、开始/结束时间、结果、报告路径和限制。最终验收报告由 manifest 生成，
不得手写“全部通过”。最低 requirement ID：

| ID | 结论 | 主要证据 |
|---|---|---|
| V17-CONTRACT | API/错误码/配置/DB/协议兼容 | 快照 diff、冻结测试报告 |
| V17-RECOVERY | 重启、断连、乱序、回滚、对账可恢复 | 故障注入和真实行为测试 |
| V17-UPGRADE | 历史版本可升级且可备份恢复 | 历史 fixture、Flyway、恢复校验 |
| V17-SOAK | 长稳无状态/资源漂移 | 时间序列、GC/ClassLoader/线程报告 |
| V17-PERF | 性能无不可接受退化 | 固定 runner 基线和原始样本 |
| V17-COMPAT | 正式支持矩阵全部通过 | CI matrix 汇总 JSON |
| V17-OPS | 探针、指标、诊断、告警可用 | 故障测试、脱敏测试、演练记录 |
| V17-SUPPLY | 发布物可验证和可追溯 | hash、SBOM、扫描、签名、provenance |
| V17-LTS | 支持/弃用/回补规则已冻结 | 策略评审和发布清单 |
| V17-REGRESSION | V1.1～V1.6 能力无回归 | 全量测试和 V1.X 最终生命周期验收 |

## 13. 完成定义

“代码写完”不等于 V1.7 完成。只有 M0～M6 交付完成，PR/RC/发布三级门禁全部满足，正式支持矩阵没有
缺证据组合，V1.1～V1.6 行为无回归，长期 soak 与供应链发布在受控环境完成，并由独立验收确认后，才允许：

1. 合并最终缺陷修复；
2. 生成并签名最终发布物；
3. 创建 annotated tag `V1.7.0`；
4. 宣布 V1.X 功能封版并进入 V1.7.x LTS 维护。
