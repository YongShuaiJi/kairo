# V1.7 LTS 支持、弃用与回补策略

> 适用版本：Kairo `V1.7.0` 和后续 `V1.7.x`。
> 技术实施与门禁：[V1.7 技术实施方案](./v1.7-lts-stabilization.md)。
> 状态：V1.7.0 发布前实施基线；发布后任何政策变化必须版本化并进入 release manifest。
> 原则：只承诺有真实证据、维护责任和可执行恢复方式的范围。

## 1. LTS 的含义

V1.7.0 是 V1.X 最后一个功能版本。这里的 LTS 不是“支持所有 JVM、框架和企业部署”，而是：

- V1.7.x 生命周期内保持 V1 API、错误码、配置、数据库迁移和 Agent V1 协议向后兼容；
- 在正式支持矩阵内修复安全、正确性、数据完整性、恢复、兼容性和资源泄漏缺陷；
- 每个维护版本继续通过适用的契约、恢复、兼容、运维和发布门禁；
- 不借维护版本增加新增强位置、规则语义、脚本权限、产品 API 或基础设施依赖；
- 不把未经测试的环境写成“理论支持”。

V1.7 的核心维护对象是“增强—运行—对账—卸载—故障恢复”闭环，不是无限扩大产品形态。

## 2. 两阶段完成状态

### 2.1 Engineering Complete

表示 M0～M5 的产品代码、测试 harness、CI、运维和发布构建已经完成，所有 PR 门禁通过，候选发布物可以从
干净源码生成。

Engineering Complete 不表示：

- 7 天 soak 已完成；
- 最终兼容矩阵已在候选 commit 上通过；
- 最终 artifact 已签名；
- LTS 支持日期和维护责任方已经生效；
- 可以创建 `V1.7.0` tag。

### 2.2 LTS Certified

表示 M6 的最终兼容、升级、恢复、2 小时 RC、7 天 soak、供应链和独立验收全部通过，release manifest 已填写
支持日期、责任方和批准信息，最终 artifact 已发布并创建 annotated tag `V1.7.0`。

任何外部环境、运行时间或签名条件尚未满足时，只能保持 Engineering Complete，不能用单元测试或文档声明替代。

## 3. 正式支持边界

### 3.1 控制面拓扑

V1.7.0 LTS 正式支持：

- 一个活跃的 Platform API + scheduler 进程；
- PostgreSQL 16 作为权威数据库；
- Redis 7 作为可选 fencing sequence 组件；
- 独立 Platform Web；
- Agent 主动向 Platform 注册、心跳和轮询命令；
- Platform 进程重启恢复。

V1.7.0 不承诺：

- 多 Platform 主动—主动或自动 leader election；
- Kubernetes/Helm/Service Mesh；
- 多区域容灾；
- MySQL、Oracle、SQL Server 生产运行；
- Redis 保存权威业务状态。

PostgreSQL 是唯一权威状态。Redis 丢失不能造成规则、发布计划、执行、卸载或审计事实丢失。

### 3.2 候选正式矩阵

最终正式矩阵必须由 `compatibility-result.json` 生成。V1.7.0 候选范围固定为：

- Platform：Linux x86_64、JDK 21；
- 目标 JVM：JDK 17、21；
- 加载方式：premain、agentmain、外部 attach；
- 基础目标：普通 Java 和 Spring Boot 3；
- ClassLoader/动态形态：父子同名、JDK Proxy、CGLIB、Byte Buddy、Lambda、bridge/synthetic；
- 兼容行为：首次加载、retransform、redefine/hot update、精确卸载和一个固定 Byte Buddy Agent 共存 fixture。

macOS arm64/JDK 21 只有在真实 CI 完整执行对应矩阵行后才能进入正式支持，否则为 `EXPERIMENTAL`；
该证据不自动扩展为 macOS/JDK 17 支持。

以下项目在 V1.7.0 默认不是正式支持：

| 组合 | 默认状态 | 说明 |
|---|---|---|
| JDK 8/11 完整 Agent | `NOT_SUPPORTED` | Java 8 bootstrap jar 不等于 modern core 可运行 |
| Windows | `EXPERIMENTAL` | 需要真实 attach/增强/卸载 CI 才能提升 |
| Spring Boot 2 | `EXPERIMENTAL` | V1.7 不建设第二套旧核心发行物 |
| Kotlin 默认参数/协程 | `EXPERIMENTAL` | JVM 形态局部测试不等于语言正式支持 |
| 独立 Tomcat 部署 | `EXPERIMENTAL` | 没有真实 fixture 前不承诺 |
| 多 Platform 节点 | `NOT_SUPPORTED` | 超出当前单进程架构 |

`SKIPPED`、`NOT_RUN`、`continue-on-error`、只编译成功、版本探测或模拟 OS 均不能升级支持等级。

### 3.3 支持声明生成

最终发布时：

- CI 为每个矩阵行生成状态、环境、命令、报告和 build ID；
- 汇总任务生成 `target/v1.7/compatibility-result.json`；
- `docs/compatibility/v1.7.md` 和 release manifest 必须由同一 JSON 生成；
- 候选正式行存在 `FAILED/SKIPPED/NOT_RUN` 时阻断发布；
- 不允许人工把失败行改写为支持，除非先修改实施方案、说明风险并重新评审。

## 4. 生命周期和支持日期

支持期限不在代码中虚构。只有发布责任和资源确定后，才能在最终 release manifest 填写：

```text
ltsStart
standardSupportEnd
securitySupportEnd
maintainer
securityContact
releaseApprover
```

规则：

- 上述字段未确定前，不对外承诺具体支持年限；
- standard support 结束后，只接受符合政策的安全和 P0/P1 修复；
- security support 结束即进入 EOL；
- EOL 至少提前 90 天公告，给出最后支持版本、最后安全版本和迁移路径；
- EOL 后不默认承诺紧急安全修复，由维护方单独决定。

## 5. 缺陷等级

| 等级 | 定义示例 | 发布处理 |
|---|---|---|
| P0 / Critical | 可利用 RCE、认证绕过、权限边界突破、不可恢复的数据或目标 JVM 破坏、错误恢复到第三方字节码之前 | 立即停止/撤回受影响发布；优先缓解和修复 |
| P1 / High | 无可靠规避的错误增强/卸载、正式规则错误复活、状态永久漂移、广泛不可用、严重泄密 | V1.7.x 最高优先级；发布前必须清零 |
| P2 / Medium | 有稳定规避方式的兼容、恢复、性能或诊断缺陷 | 必须有 owner、规避方式和目标版本 |
| P3 / Low | 低影响体验、非关键诊断或文档缺陷 | 按维护容量安排 |

对外修复 SLA 只有在维护责任方、通知渠道和发布能力明确后才能承诺。内部响应目标放入安全/运维流程，不能在
无人承担时写不可兑现的固定天数。

## 6. 版本、分支和 tag

- `V1.7`：LTS 集成和维护分支；
- `bugfix/v1.7-<scope>`：单个缺陷或安全修复分支；
- Maven/Web/Docker 产品版本：`1.7.0`、`1.7.1`……；
- Git tag：`V1.7.0`、`V1.7.1`……，均为 annotated tag；
- 最终 tag 必须指向通过对应 release manifest 验证的发布 commit；
- patch 版本不得包含破坏性 API/协议/配置/迁移变化或新产品能力。

若 `main` 已发展 V2：

- 同时影响当前开发线和 LTS 的缺陷，先在能够验证根因的开发线修复，再做 LTS 适配；
- 只存在于 LTS 的缺陷直接在 `bugfix/v1.7-<scope>` 修复；
- 禁止机械 cherry-pick 大提交后不做 LTS 风险分析和回归。

## 7. 回补准入

### 7.1 可以回补

- 已确认的安全漏洞、认证和权限边界缺陷；
- 数据一致性、命令 fencing、错误增强、错误卸载、重启恢复和幂等缺陷；
- 正式支持矩阵内的兼容回归；
- 有基线证明的性能或资源泄漏修复；
- health、指标、支持包、构建可复现、SBOM、签名和文档修复；
- 为保持已冻结契约兼容所必需的最小修复。

### 7.2 不可回补

- 新增强位置、规则语义、脚本档位、脚本权限或产品 API；
- 新 Web 产品页面、AI/MCP 工具或业务资源族；
- 为方便实现而修改 V1～V41 已发布迁移；
- 无证据的大规模重构、框架升级或模块拆分；
- JDK 8/11、Windows、多 Platform 等非支持范围扩展；
- 需要新中间件或改变默认运行拓扑的工作；
- 没有测试、没有风险分析或无法安全缓解/回退的修改。

### 7.3 每个回补必须提供

1. 缺陷复现、影响版本、严重等级和根因；
2. 为什么适合 LTS 的最小修复说明；
3. API、协议、配置、DB、权限、字节码恢复和性能风险分析；
4. 修复前失败、修复后通过的自动化测试；
5. 所有 PR 门禁及受影响的 RC 门禁；
6. 至少一个与缺陷风险匹配的真实 JVM 或真实部署证据；
7. 缓解/回退方式、CHANGELOG 和已知限制更新；
8. 更新后的 acceptance/release manifest。

安全修复可以限制公开细节，但内部证据和批准不能省略。

## 8. 弃用和移除

- V1 API、公开错误码、配置键和 Agent V1 协议在整个 V1.7.x 生命周期内不得破坏性移除。
- 新弃用必须同时提供 replacement、迁移说明、`deprecated` 元数据和计划移除的大版本。
- 不得在 V1.7.x 内先弃用后移除；最早在 V2 移除。
- 错误码不得复用为不同含义；废弃错误码保留原结构或提供明确兼容映射。
- 配置改名采用“旧键继续有效、新键优先、同时出现时结构化诊断”，不能让旧部署静默改变行为。
- Agent additive 协议字段必须有旧端缺失时的明确默认值；平台不能在 capability 协商前发送新命令。
- 新数据库结构只能追加 migration；已发布 migration 永不改写。

自动 schema diff 负责阻止技术破坏，弃用理由和移除决定仍需人工评审。

## 9. 安全与依赖维护

- 漏洞判断基于最终 CycloneDX SBOM、可达性和影响分析，不只看扫描器分数。
- Critical/High 默认阻断；例外必须包含 owner、理由、缓解、到期日和复核条件。
- 依赖升级采用修复问题所需的最小安全版本，验证许可证、API/字节码兼容、Agent 体积和真实运行行为。
- 脚本沙箱、UNRESTRICTED、attach、鉴权、Token、诊断脱敏和远程命令改动视为高风险。
- Token、Authorization、脚本正文、原始 class bytes 和环境变量密值不得进入日志、支持包、manifest 或 provenance。
- 疑似漏洞使用仓库公布的私密渠道，不在公开 issue 提前暴露利用细节。

V1.7.x 不通过接入 Vault、云 KMS 或新身份系统来解决局部安全缺陷；此类需求进入独立版本设计。

## 10. 维护版本发布门禁

每个 V1.7.x 必须：

- 从干净 checkout 构建，version、commit、tag 和 build identity 一致；
- 通过冻结契约、完整 Maven/Web 回归和受影响专项门禁；
- 对受影响支持矩阵行重新执行真实测试；
- 生成 artifact hash、CycloneDX SBOM、漏洞/许可证报告、cosign 签名和 provenance；
- 发布 CHANGELOG、升级/回退说明、支持矩阵变化和已知限制；
- 保存 release manifest 和可访问证据；
- 证明修复不会错误恢复字节码、扩大目标范围或复活过期规则。

低风险文档修订可以不重新运行 7 天 soak；涉及 Agent 热路径、ClassLoader、规则恢复、命令状态机或数据库一致性
的维护版本，至少重新执行 10,000 cycle 和 2 小时 RC soak。是否重新执行 7 天 soak 由风险评审记录决定。

## 11. 撤回与安全事件

出现以下情况时应暂停分发并评估撤回：

- P0/Critical；
- 供应链污染或签名/provenance 不可信；
- 不可恢复的数据损坏；
- 错误增强、错误卸载或破坏其他 Agent 变换；
- 正式规则在 JVM 重启后错误复活/丢失且没有可靠缓解。

撤回不能删除历史事实。必须：

- 标记受影响版本和 artifact；
- 发布影响范围、缓解和恢复步骤；
- 保留原 release manifest 和证据；
- 发布新的修复版本和新的 tag，不移动或覆盖旧 tag。

## 12. 治理边界

自动化可以证明 schema、测试、矩阵和 artifact，但不能替代以下决定：

- 是否扩大正式支持矩阵；
- 缺陷严重等级；
- 漏洞/许可证例外风险；
- 是否允许回补；
- 支持日期和维护责任；
- 最终发布或撤回批准。

这些决定必须进入 release manifest，包含责任方和依据。禁止通过检查 Markdown 是否存在、打印 warning、
`continue-on-error` 或手写“全部通过”制造虚假 LTS 结论。
