# V1.7 LTS 支持、弃用与回补策略

> 适用版本：Kairo `V1.7.0` 及 `V1.7.x`。
> 技术门禁：[V1.7 LTS 技术方案](./v1.7-lts-stabilization.md)。
> 状态：V1.7.0 发布前冻结；发布后的政策变更必须留下版本化变更记录。

## 1. 产品生命周期

V1.7.0 是 V1.X 的最后一个功能版本。进入 LTS 后：

- 接受安全、正确性、数据完整性、可靠性、兼容性和明确有测量依据的性能修复；
- 接受诊断、文档、构建与供应链修复，但不得借此增加新的业务能力；
- 新增强位置、新规则语义、新脚本权限、新 API 产品能力和新产品域进入 V2.0；
- 每个维护版本必须继续通过冻结契约和适用的 V1.7 验收门禁。

支持期限不在代码中虚构固定日期。V1.7.0 发布时必须在 release manifest 填写
`ltsStart`、`standardSupportEnd`、`securitySupportEnd` 和维护责任方；日期未确定前不得对外承诺具体年限。
EOL 至少提前 90 天公告，并说明最后安全版本和迁移路径。

## 2. 正式支持矩阵

正式矩阵由候选版的机器可读兼容报告生成，不能由本文提前宣布。规则如下：

- 只有状态为 `PASSED` 且报告可追溯到最终候选 commit 的组合，才能列为正式支持；
- `SKIPPED`、`NOT_RUN`、`continue-on-error` 或只编译成功均不能成为支持证据；
- `EXPERIMENTAL` 只能表示可试用，不进入 SLA；
- Platform 运行 JDK、Agent class-file target 和被注入目标 JVM 分开声明；
- OS、JDK、框架、ClassLoader、动态类和附加方式的最小风险组合必须在技术方案 W3 中执行。

当前代码事实是 reactor 以 Java 17、Spring Boot 3.3 构建。JDK 8/11 目标 JVM、Spring Boot 2、Windows、
Kotlin 等是否进入正式支持，以 V1.7 RC 真实端到端结果为准；在证据产生前均属于待验证，不得先写为支持。

发布时将最终矩阵写入 `docs/compatibility/v1.7.md` 和 release manifest，二者必须由同一 CI 汇总结果生成。

## 3. 缺陷等级与响应目标

| 等级 | 示例 | 维护处理 |
|---|---|---|
| P0 / Critical | 可利用 RCE、认证绕过、跨租户/权限边界、不可恢复的数据或目标 JVM 破坏 | 立即停止相关发布；确认、缓解、修复和公告按安全响应流程处理 |
| P1 / High | 无规避方案的错误增强/卸载、数据不一致、广泛不可用、严重泄密 | 当前维护版本最高优先级，发布前必须清零 |
| P2 / Medium | 有可靠规避方式的功能、兼容或性能缺陷 | 指定 owner、规避方式和目标维护版本 |
| P3 / Low | 低影响体验、诊断或文档问题 | 按维护容量排期 |

对外修复 SLA 只有在维护责任方、通知渠道、支持期限和发布能力明确后才能承诺。内部响应目标在
`SECURITY.md` / 运维流程中维护；不得在无人承担时写“7 天修复”之类不可兑现的保证。

## 4. 版本与分支

- `V1.7`：LTS 集成分支；维护版本从此分支发布。
- `bugfix/v1.7-<scope>`：单个缺陷或安全修复分支，验收后合并回 `V1.7`。
- tag：`V1.7.0`、`V1.7.1`……均为 annotated tag，并指向已验证且已签名的发布 commit。
- 版本语义：patch 版本不得包含破坏性 API/协议/配置/迁移修改或新产品能力。

若仓库继续在 `main` 发展 V2，修复应先在受影响的当前开发线完成，再按风险回补；若缺陷只存在于 LTS，
可以直接在 bugfix 分支修复。禁止机械 cherry-pick 后不做 LTS 适配和回归。

## 5. 回补准入与流程

### 5.1 可以回补

- 已确认的安全漏洞和权限边界缺陷；
- 数据一致性、错误增强、错误卸载、恢复、幂等和协议兼容缺陷；
- 正式支持矩阵内的回归；
- 有基线证明且风险可控的性能/资源泄漏修复；
- 构建可复现、SBOM、签名、诊断、文档和测试修复。

### 5.2 不可回补

- 新业务能力、新公开 API、新规则语义或扩大权限；
- 为方便实现而修改已发布迁移；
- 无法证明向后兼容的大规模重构或依赖升级；
- 只在非支持组合出现且会提高正式支持风险的适配；
- 没有测试、没有风险分析或无法安全回退的修改。

### 5.3 每个回补必须提供

1. 缺陷复现、影响版本、严重等级和根因；
2. 最小修复及为何适合回补的说明；
3. API/协议/配置/DB/权限/性能风险分析；
4. 修复前失败、修复后通过的自动化测试；
5. PR 必跑门禁；高风险修复还必须执行相关 RC 门禁；
6. 回退或缓解办法、CHANGELOG 和已知限制更新。

安全修复可以限制公开细节，但内部证据和审批不能省略。

## 6. 弃用与移除

- V1 API、错误码、配置和 Agent 协议在整个 V1.7.x 生命周期内不得破坏性移除。
- 新弃用必须同时提供替代能力、迁移说明、`deprecated` 元数据和计划移除的**大版本**。
- 不得在同一个 LTS 系列内先弃用后移除；最早在 V2 执行移除，并提供兼容/迁移说明。
- 错误码不得复用为不同含义；废弃码保留并返回原有结构或明确兼容映射。
- 配置改名采用旧键兼容 + 新键优先 + 冲突诊断，不得让旧部署静默改变行为。

自动化 schema diff 和冻结测试负责阻止技术破坏；弃用理由、替代方案和移除决策仍必须经人工评审。

## 7. 安全与依赖维护

- 漏洞判断以最终发布 SBOM 和可达性/影响分析为依据，不只看扫描器分数。
- Critical/High 默认阻断发布；例外必须记录 owner、理由、缓解、到期日和复核条件。
- 依赖升级采用最小安全版本，必须验证许可证、API/字节码兼容、Agent 体积与运行行为。
- 涉及脚本沙箱、attach、鉴权、Token、诊断脱敏或远程命令的修改视为高风险，必须有针对性安全测试。
- 发现疑似漏洞时避免在公开 issue 泄露利用细节，使用仓库公布的私密报告渠道。

## 8. 发布、撤回与 EOL

每个 V1.7.x 发布必须：

- 从干净 checkout 构建，版本号、commit 和 tag 一致；
- 通过契约冻结、全量回归和受影响专项门禁；
- 生成并验证 artifact hash、SBOM、安全报告、签名和 provenance；
- 发布 CHANGELOG、升级/回退说明、支持矩阵变化和已知限制；
- 保存 release manifest 和可访问的验收证据。

若发布后发现 P0、供应链污染或不可恢复的数据/增强问题，应暂停分发并撤回受影响版本；不能删除历史事实，
而应发布公告、标记受影响 artifact、提供缓解和修复版本。

进入 EOL 前必须给出替代版本、迁移路径、最后支持日期和最后安全版本。EOL 后是否接受紧急安全修复由维护方
单独决定，不能默认承诺。

## 9. 治理边界

自动化可以证明 schema、测试和产物，但不能替代以下决定：支持组合是否足够、严重等级、例外风险、回补价值、
支持期限和最终发布批准。这些结论必须在 release manifest 中记录责任方和依据，避免用“测试 Markdown 是否存在”
之类形式化门禁制造虚假安全感。
