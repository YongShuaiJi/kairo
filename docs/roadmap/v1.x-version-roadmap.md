# Kairo V1.X 版本迭代路线图

> 文档状态：已确认的 V1.X 功能规划
> 规划范围：V1.1 至 V1.7 LTS
> 基线版本：V1.0 运行时方法增强闭环

对应的落地设计见 [V1.X 技术改造方案索引](./v1.x-technical/README.md)。

## 1. 规划背景

Kairo V1.0 已经完成 Java Agent 接入、目标方法发现、Groovy 规则编写与校验、规则发布、
运行时方法增强、执行观察以及卸载恢复的基础闭环。

V1.X 后续版本不再围绕零散的故障类型持续增加功能，而是把方法增强建设成一项完整、
通用、透明、可组合、可恢复，并且能被人、AI 和自动化系统稳定控制的基础能力。

V1.X 的最终产品定义是：

> 对已经加载或将要加载的 JVM 方法，Kairo 能够在关键执行位置进行透明、任意、可组合、
> 可观察、可验证、可恢复的运行时增强，并通过公开接口支持人工和 AI 完成完整生命周期管理。

## 2. V1.X 总体边界

### 2.1 V1.X 必须完成的能力

1. 展示 JVM 中增强前、预计增强后和实际增强后的代码及字节码差异。
2. 提供从安全模式到完整 Groovy/JVM 权限的分级脚本能力。
3. 覆盖方法入口、返回、异常、构造器、内部调用点等关键增强位置。
4. 支持同一目标上的多规则组合、顺序执行、冲突检测和局部卸载。
5. 保证增强和卸载可验证、可重复，并避免误伤其他 Java Agent 的修改。
6. 兼容多 ClassLoader、代理类、Lambda、动态生成类及主流 JDK 场景。
7. 开放完整 API，并为 AI、CLI 和流水线提供任务级自动化接口。
8. 通过性能、长稳、压力、升级和兼容性验证，形成长期维护版本。

### 2.2 V1.X 明确不扩展的方向

以下方向不作为 V1.X 方法增强封版的前置条件，应在 V2.0 或独立项目中规划：

- 流量录制、数据集提取和批量回放；
- 分布式故障实验与跨服务场景编排；
- 通用 APM、日志检索和全链路追踪；
- 堆内存任意修改、对象浏览器和单步调试器；
- 类结构修改，例如运行时增加字段、增加方法或修改继承关系；
- Kubernetes、大规模多区域部署和企业身份系统。

### 2.3 版本顺序

| 版本 | 主题 | 核心结果 |
| --- | --- | --- |
| V1.1 | 增强可视化与运行时底座 | 看得清、可预览、可诊断 |
| V1.2 | 脚本能力全面开放 | 从有限 Mock 升级为通用运行时增强 |
| V1.3 | 扩展增强位置 | 覆盖方法内部和构造过程的关键位置 |
| V1.4 | 多规则增强链与可靠恢复 | 可组合、可局部卸载、可与其他 Agent 共存 |
| V1.5 | 现代 JVM 场景兼容 | 在复杂 ClassLoader、代理和动态类环境中准确工作 |
| V1.6 | API First 与 AI First | 页面、AI、CLI 和流水线使用同一套公开能力 |
| V1.7 LTS | 稳定性验证与封版 | 完成性能、长稳、升级和兼容性收口 |

V1.1 至 V1.6 的详细模块改造、数据协议、测试矩阵和智能体交付要求：

## 3. V1.1：增强可视化与运行时底座

### 3.1 版本目标

建立权威的运行时字节码基线和转换历史，使使用者能够明确回答：

- 目标类在 Kairo 介入前是什么状态；
- Kairo 计划对它做什么修改；
- JVM 当前实际运行的字节码是什么；
- 增强失败时失败在哪一个转换阶段。

### 3.2 主要工作

#### 字节码基线与版本管理

- 捕获 Kairo 本次转换开始时收到的 class bytes，作为本次增强基线。
- 保存 Kairo 增强后的 class bytes、哈希和转换元数据。
- 使用类名、ClassLoader ID、类版本共同标识目标类。
- 记录增强、重新转换、局部卸载和完全恢复的转换历史。
- 区分 JVM 初始字节码、Kairo 收到的输入基线和 Kairo 输出字节码。
- 避免使用过早保存的“原始字节码”覆盖其他 Transformer 后续产生的修改。

#### 增强前后对比

- 提供 Before/After Java 反编译视图。
- 提供 JVM 字节码指令级 Before/After 视图。
- 支持结构化 Diff 和修改位置高亮。
- 标记 Kairo 插入的 Advice、Bridge、分支和异常处理逻辑。
- 明确标识反编译结果是近似源码，字节码视图是权威结果。
- Arthas 可作为结果验证和可选集成工具，但 Kairo 核心能力不依赖完整 Arthas 进程。

#### 发布前预览和发布后验证

- 在不修改目标 JVM 的情况下生成预计增强结果。
- 发布后重新获取 JVM 实际运行字节码。
- 对比预计结果与实际结果并展示哈希。
- 支持导出增强前后 class 文件，用于离线分析。
- 对反编译、字节码校验、类转换失败提供明确诊断。

#### 基础诊断 API

- 查询目标类身份和当前转换状态。
- 获取基线字节码、预计字节码和实际字节码。
- 获取反编译结果和字节码 Diff。
- 执行只读增强预览。
- 查询转换历史及失败原因。

### 3.3 交付物

- Agent 字节码快照和转换历史模块；
- 反编译器适配接口及默认实现；
- 字节码指令 Diff 服务；
- 增强预览及发布后验证 API；
- Web Before/After 对比页面；
- 与 Arthas 等外部工具的对照测试用例。

### 3.4 验收标准

- 同名类位于不同 ClassLoader 时能够正确区分，不串用快照。
- Before 和 After 均能追溯到明确的 class bytes 及 SHA-256 哈希。
- 增强预览不修改目标 JVM 的运行状态。
- 发布后展示的实际字节码与 Agent 从 JVM 获取的结果一致。
- 反编译失败时仍能查看字节码指令、哈希和失败原因。
- 多次增强和卸载后，转换历史完整且顺序正确。
- 字节码采集和反编译不在业务请求线程中执行耗时工作。
- 诊断和对比能力能够完全通过公开 HTTP API 使用。
- 使用外部工具读取目标类时，关键字节码结构与 Kairo 展示结果一致。

## 4. V1.2：脚本能力全面开放

### 4.1 版本目标

把当前有限的故障注入脚本提升为分级开放的通用 JVM 脚本增强能力。Kairo 提供安全默认值，
同时允许部署方和应用负责人显式启用完整权限。

### 4.2 主要工作

#### 能力等级

- `SAFE`：保持当前受限语法和受控 Mock API，作为默认等级。
- `EXTENDED`：开放常用 import、集合、JSON、时间和经过配置的工具类。
- `UNRESTRICTED`：开放完整 Groovy 语法及 JVM 能力。
- 支持平台级默认值、应用级上限和规则级选择。
- 能力等级、修改人和生效范围进入审计记录。

#### 完整 Groovy/JVM 权限

在 `UNRESTRICTED` 模式下允许：

- 任意 import；
- 文件和 IO；
- 网络访问；
- 反射和 ClassLoader；
- 线程及并发工具；
- 调用目标应用内部类和第三方依赖；
- 创建复杂对象；
- 完整 Groovy 控制结构、方法和闭包能力。

#### 脚本类加载语义

- 默认以目标方法所属 ClassLoader 解析业务类。
- 支持在多 ClassLoader 候选中显式选择。
- Agent 自身依赖与业务应用依赖保持隔离。
- 类不可见、版本冲突和链接错误返回结构化诊断。
- 校验、试用和正式发布采用一致的编译与类加载语义。

#### 最低运行时保护

完整权限不取消 JVM 可恢复性保护：

- 规则 TTL；
- 最大命中次数；
- 连续失败自动停用；
- 应用级和 Agent 级紧急停止；
- 脚本执行耗时、失败次数和资源使用观测；
- 脚本异常默认 fail-open，不改变原业务行为；
- 所有高权限操作完整审计。

需要明确：JVM 内线程无法依靠普通中断安全终止，因此“超时”首先用于检测、熔断后续执行和告警，
不能承诺对任意恶意或永久阻塞代码进行强制、无损终止。

#### 脚本试用

- 仅编译和静态校验，不发布规则。
- 使用模拟参数执行脚本。
- 在真实目标 JVM 中创建短生命周期试用规则。
- 返回日志、决策、耗时、异常和类型转换结果。
- AI 或客户端断开后，试用规则仍按 TTL 自动卸载。

### 4.3 交付物

- 分级脚本安全策略；
- 应用级能力配置和审计；
- 目标 ClassLoader 感知的脚本编译器；
- 临时脚本会话和试用 API；
- TTL、失败熔断和紧急停止能力；
- 三个能力等级的安全说明和示例。

### 4.4 验收标准

- `UNRESTRICTED` 脚本能够使用 IO、网络、反射、线程和目标应用类。
- `SAFE`、`EXTENDED`、`UNRESTRICTED` 的行为边界有自动化测试覆盖。
- 应用不允许完整权限时，规则不能绕过应用级上限。
- 校验、试用和正式发布使用一致的 ClassLoader 解析结果。
- 脚本编译或执行异常默认不改变原方法行为。
- 连续失败达到阈值后，后续执行自动熔断并产生事件。
- 临时规则在正常完成、客户端断开和 Platform 不可用时均能按 TTL 失效。
- 紧急停止不依赖 Groovy 脚本自身配合。
- 完整权限的启用、使用和停用均可审计。
- 本版本所有操作均有公开 API，不要求必须使用 Web 页面。

## 5. V1.3：扩展增强位置

### 5.1 版本目标

从方法进入、正常返回和异常退出，扩展到构造过程、最终退出和方法内部调用点，覆盖通用方法增强
最有价值的关键执行位置。

### 5.2 主要工作

#### 完善方法级位置

- 方法进入 `BEFORE`；
- 正常返回 `RETURN`；
- 异常退出 `THROWS`；
- 无论成功或失败均执行的 `FINALLY`；
- 参数读取和修改；
- 返回值读取和修改；
- 异常替换、异常恢复和正常结果转异常。

#### 构造器增强

- 构造器参数处理；
- 对象完成初始化后的增强；
- 构造失败时的异常增强；
- 识别 `this()`、`super()` 调用边界；
- 防止在对象尚未完成初始化时读取非法实例状态。

#### 方法内部调用点增强

- 按被调用类、方法名和 JVM 描述符匹配调用点。
- 支持调用前、正常返回和异常位置。
- 同一方法存在多个相同调用点时支持按索引或字节码位置选择。
- 支持修改调用参数、短路调用、修改返回值和替换异常。
- 发布前展示匹配到的方法、调用点数量和具体位置。

#### 特殊方法识别

- 静态、私有、final、synchronized 方法；
- 默认接口方法；
- bridge 和 synthetic 方法；
- native 和 abstract 方法提前标记为不可直接增强；
- 不支持或高风险场景在发布前给出明确原因。

### 5.3 交付物

- 统一增强位置模型；
- 构造器 Advice；
- 调用点匹配和字节码改写模块；
- 增强位置预览与选择界面；
- 各位置的脚本上下文定义；
- 位置级 API、错误码和自动化测试。

### 5.4 验收标准

- 每一种承诺的增强位置均有正向、异常和卸载测试。
- 构造器增强通过 JVM 字节码校验，不访问未初始化对象。
- 调用点能够准确区分方法重载和 invoke 指令类型。
- 相同调用点出现多次时，可以稳定定位到指定位置。
- 调用点规则能够独立启用、停用和卸载。
- 增强后的控制流、栈帧和异常表通过 JVM 校验。
- native、abstract 等不支持场景在转换前被拒绝。
- 任一位置增强失败时，原类仍能加载并保持原业务行为。
- 发布预览能够准确展示匹配数量和预期修改位置。
- 所有新增位置均支持公开 API 和 V1.1 的 Before/After 对比。

## 6. V1.4：多规则增强链与可靠恢复

### 6.1 版本目标

允许同一目标上存在多条规则，建立确定的执行、冲突和卸载语义，并保证 Kairo 的恢复操作不会
误删其他 Java Agent 的增强结果。

### 6.2 主要工作

#### 多规则增强链

- 同一方法和调用点支持多条规则。
- 定义全局一致的优先级和同优先级排序规则。
- 定义 BEFORE、RETURN、THROWS、FINALLY 各阶段的链式执行顺序。
- 定义参数、返回值和异常在规则间的传递方式。
- 定义短路返回、异常抛出、异常恢复后的后续规则行为。
- 支持规则继续、终止传播和互斥策略。

#### 冲突检测

- 检测多条规则同时替换返回值或异常。
- 检测同一参数或调用点的冲突修改。
- 检测由提前短路导致的不可达规则。
- 检测不兼容的能力等级和运行条件。
- 支持拒绝发布、显式排序、互斥或经确认后组合。
- 发布预览必须展示最终增强链和冲突结论。

#### 版本、事务与幂等

- 每条增强链拥有单调版本号和内容哈希。
- 所有发布和卸载命令携带幂等键及期望版本。
- 多类、多方法发布采用全成功或回滚语义。
- 防止延迟到达的旧命令覆盖较新状态。
- Agent 在操作中途退出后，重连时自动进行期望状态与实际状态对账。

#### 精确卸载

- 卸载一条规则时保留同目标上的其他规则。
- 卸载一个位置时保留同方法上的其他位置。
- 最后一条 Kairo 规则删除后恢复到 Kairo 本轮转换的正确输入基线。
- 卸载后重新读取实际字节码并校验结果。
- 卸载失败进入可重试、可诊断的确定状态。

#### 其他 Agent 共存

- 明确 Transformer 注册顺序和 retransformation 语义。
- 避免缓存过早的原始字节码用于强制覆盖。
- 验证与 APM、Arthas、JaCoCo、热更新工具及其他 Byte Buddy/ASM Agent 共存。
- 无法保证无损恢复的场景必须提前拒绝或明确提示，不能假报成功。

### 6.3 交付物

- 增强链领域模型和执行引擎；
- 冲突分析器；
- 链版本、哈希、幂等和事务机制；
- Agent 状态对账与离线补偿；
- 精确局部卸载实现；
- 其他 Agent 共存测试套件。

### 6.4 验收标准

- 同一方法上的规则执行顺序在发布、重启和重连后完全一致。
- 参数、返回值和异常按照文档定义在增强链中传递。
- 短路、终止传播和互斥规则具备确定行为。
- 冲突规则在发布前被发现并提供机器可读的冲突原因。
- 任意单条规则可以卸载，不影响其他 Kairo 规则。
- 重复发布和重复卸载具备幂等性。
- 多目标发布中任一转换失败时能够完整回滚或保持旧版本。
- Agent 中途退出后，重连能够自动恢复到平台期望状态。
- 延迟旧命令不能覆盖新版本增强链。
- 在约定的共存矩阵中，Kairo 卸载不删除其他 Agent 的增强。
- 完成至少 1,000 次增强、组合、局部卸载循环，最终字节码与预期一致。

## 7. V1.5：现代 JVM 场景兼容

### 7.1 版本目标

证明 Kairo 在真实、复杂的现代 JVM 环境中仍能准确定位、增强、重新增强和卸载目标方法。
本版本专注 JVM 与框架兼容，不混入 AI 产品接口建设。

### 7.2 主要工作

#### ClassLoader 场景

- 多 ClassLoader 中的同名类；
- Bootstrap ClassLoader；
- Spring Boot Launcher ClassLoader；
- Tomcat 等 Web 容器 ClassLoader；
- 插件化、子应用和可热卸载 ClassLoader；
- 类卸载后清理规则、缓存和观察数据中的强引用。

#### 代理与动态生成类

- JDK 动态代理；
- CGLIB 和 Spring AOP；
- Byte Buddy 等工具生成的动态类；
- Lambda 及相关 synthetic 方法；
- bridge 方法和泛型擦除场景；
- 明确展示当前选择的是代理类、目标类还是二者。

#### 类生命周期

- 目标类尚未加载时预注册规则。
- 类首次加载时自动增强。
- 类重新定义、热更新后自动对账和按策略重新增强。
- 类卸载后释放 ClassLoader 相关状态。
- 动态类无法稳定重现时返回明确状态，不假报永久生效。

#### 兼容矩阵

最低正式支持矩阵：

- JDK 8、11、17、21；
- Spring Boot 2.x、3.x；
- premain、agentmain 和动态 attach；
- Java 编译类；
- Kotlin 常用方法、默认参数和协程边界根据测试结果标记支持等级。

Scala、Groovy 应用类、OSGi 和特定商业容器根据实际用户需求列为验证支持或后续适配，
不默认承诺完整支持。

### 7.3 交付物

- ClassLoader 精确身份及生命周期管理；
- 代理目标解析和选择策略；
- Lambda、bridge、synthetic 方法发现支持；
- 类预注册、重新加载和重新增强机制；
- 自动化 JDK/框架兼容矩阵；
- 正式支持、有限支持和不支持场景文档。

### 7.4 验收标准

- 不同 ClassLoader 中的同名类不会误增强或误卸载。
- 用户能够准确选择并识别目标 ClassLoader。
- 代理类和目标类的增强位置及影响范围清晰可见。
- JDK 动态代理、CGLIB、Spring AOP 和约定的 Lambda 场景能够发现、增强和卸载。
- 未加载类能够预注册，并在首次加载时应用正确规则。
- 类重新定义后能够自动重新增强，或返回明确的不兼容状态。
- ClassLoader 卸载后不存在由 Kairo 导致的持续强引用和明显 Metaspace 泄漏。
- JDK 与 Spring Boot 正式支持矩阵全部进入持续集成。
- V1.4 的规则组合、局部卸载及其他 Agent 共存能力无回归。
- 兼容性失败包含环境信息、目标身份、原因和恢复建议。

## 8. V1.6：API First 与 AI First

### 8.1 版本目标

页面只是 Kairo API 的一个客户端。AI、CLI、CI/CD 和其他平台应使用同一套公开、稳定、
可发现、可恢复的接口完成完整增强生命周期。

### 8.2 主要工作

#### API First

为页面已有和 V1.1 至 V1.5 新增的全部能力提供正式 API：

- 应用、环境、实例和 Agent 管理；
- 类、方法、调用点和 ClassLoader 搜索；
- 脚本编译、校验、试用和临时运行；
- 增强预览、反编译和字节码 Diff；
- 规则及版本管理；
- 增强链、排序和冲突分析；
- 发布、暂停、恢复、卸载和紧急停止；
- 命中事件、脚本日志、诊断和状态对账；
- 能力等级和应用级策略管理。

所有写 API 统一支持：

- 稳定资源 ID；
- 幂等键；
- 期望版本或乐观锁；
- 结构化错误码；
- 影响范围和风险等级；
- 恢复或撤销方式；
- 审计主体和调用来源。

#### AI 任务级接口

- 根据结构化条件或自然语言描述查找候选方法。
- 一次获取方法签名、参数结构、ClassLoader、已有规则和脚本上下文。
- 创建有 TTL 的临时脚本会话。
- 组合执行“校验、试用、增强预览”。
- 临时灰度应用规则并查询命中结果。
- 返回适合 AI 修正脚本的字段级、位置级错误信息。
- 一键提交临时会话为正式规则版本。
- 一键撤销某个 AI 会话产生的全部运行时变更。
- 会话中断后由 Agent TTL 保证自动恢复。

#### 开发者入口

- 维护完整 OpenAPI 描述和调用示例。
- 提供 CLI，覆盖完整生命周期。
- 提供至少一种官方 SDK 或从 OpenAPI 生成并验证客户端。
- 提供 MCP Server，使支持 MCP 的 AI 可直接发现和使用 Kairo 工具。
- MCP、CLI、Web 和 SDK 均调用相同的公开 Platform API，不建立旁路业务逻辑。

#### API 生命周期

- 定义 API 版本策略和兼容窗口。
- 定义字段新增、废弃和删除规则。
- 为长任务提供统一任务状态及轮询协议。
- 为事件观察提供分页、游标或流式读取协议。
- OpenAPI、错误码和权限矩阵随代码自动校验。

### 8.3 交付物

- 覆盖全部产品能力的公开 API；
- AI 临时会话和任务级复合 API；
- OpenAPI、错误码和权限矩阵；
- 官方 CLI；
- SDK 或经过验证的生成客户端；
- MCP Server；
- AI 端到端演示和自动化验收用例。

### 8.4 验收标准

- Web 不使用任何仅页面可访问的私有业务接口。
- 不打开 Web 时，客户端仍能完成目标发现、脚本编写、校验、试用、预览、发布、观察和卸载。
- AI 能根据结构化错误信息至少完成约定场景的脚本修正闭环。
- 所有写操作支持幂等键，重复请求不会产生重复资源或重复增强。
- 资源通过稳定 ID 引用，不依赖可变名称保持正确性。
- 高风险操作返回精确影响范围、风险和恢复信息。
- AI 会话中断后，临时规则能够按 TTL 自动卸载。
- OpenAPI 可以生成通过集成测试的客户端。
- CLI、MCP、Web 与 API 的执行结果一致。
- API 兼容性测试能够阻止意外删除字段、修改语义或复用错误码。
- 一个只持有适当 Token 的 AI 客户端可以完成 V1.X 全生命周期验收脚本。

## 9. V1.7 LTS：稳定性验证与最终封版

### 9.1 版本目标

不再扩展主要方法增强能力，通过性能、长稳、恢复、兼容和升级验证证明 V1.X 可以长期维护，
并正式结束 V1.X 功能开发。

### 9.2 主要工作

#### 性能与容量

- Agent 空载 CPU、堆内存、Metaspace 和线程基线。
- 已增强但规则未命中时的调用开销。
- 规则命中、脚本执行和多规则链的 P50/P95/P99 延迟。
- 大量已加载类、规则和 Agent 下的查询与匹配性能。
- 事件缓冲区满载、丢弃和背压策略验证。

#### 长稳与泄漏

- 连续运行 7 至 14 天。
- 高频增强、重新增强、局部卸载和完全卸载。
- ClassLoader 创建、增强、卸载和回收循环。
- Groovy 脚本类和脚本 ClassLoader 回收验证。
- 内存、线程、文件句柄和 Metaspace 趋势分析。

#### 故障恢复

- Platform 重启和数据库短时不可用。
- Agent 控制连接断开和恢复。
- 发布或卸载过程中 Agent 退出。
- 命令重复、乱序和延迟到达。
- JVM 重启后的规则期望状态对账。
- TTL、紧急停止和离线卸载补偿。

#### 升级与兼容

- 从 V1.0 及各 V1.X 中间版本升级到 V1.7。
- 数据库迁移、Agent 协议和 API 向后兼容验证。
- 新旧 Agent 与 Platform 的允许组合矩阵。
- 配置迁移、规则迁移和回滚说明。
- 正式冻结支持矩阵、API V1 契约和错误码。

#### 发布收口

- 完整安全审计和风险说明。
- 运维手册、故障排查手册和恢复手册。
- AI、CLI、API 和 Web 完整用户手册。
- 性能基准报告和兼容性报告。
- V1.X 已知限制和 V2.0 边界说明。

### 9.3 建议质量门槛

具体性能数值应在 V1.1 建立基准后冻结，V1.7 至少满足：

- Agent 空载资源开销不超过项目确定的发布阈值。
- 已增强但未命中的方法额外延迟满足约定的 P99 指标。
- 脚本异常和 Kairo 内部异常不传播到原业务方法。
- 完成至少 10,000 次规则状态变更后无永久状态漂移。
- 连续 7 至 14 天运行无持续性堆、Metaspace 或线程增长。
- Platform 不可用时原业务方法继续运行，TTL 规则按期失效。
- 正式兼容矩阵中的组合全部通过自动化测试。
- 所有 P0/P1 缺陷清零，P2 缺陷具有规避方案和修复计划。

### 9.4 最终验收标准

V1.7 LTS 发布必须同时满足：

1. **可观察**：可以查看真实的增强前后字节码及转换历史。
2. **可表达**：支持从安全模式到完整 JVM 权限。
3. **可定位**：覆盖承诺的方法、构造器和调用点位置。
4. **可组合**：多规则顺序、数据传递和冲突语义确定。
5. **可恢复**：支持局部卸载、事务回滚、离线补偿和状态对账。
6. **可共存**：在承诺矩阵中不会误删其他 Java Agent 的增强。
7. **可兼容**：通过主流 JDK、ClassLoader、代理和动态类验证。
8. **可自动化**：AI 不依赖页面即可完成完整生命周期。
9. **可持续**：通过性能、压力、长稳和泄漏测试。
10. **可升级**：现有 V1 用户能够平滑升级，API V1 保持兼容。

## 10. 跨版本工程规则

### 10.1 每个版本的完成定义

一个版本只有同时满足以下条件才算完成：

- 版本范围内的代码、数据库迁移和配置已经交付；
- 单元、集成、Agent 真实 JVM 和端到端测试通过；
- 新能力通过公开 API 暴露；
- OpenAPI、错误码、权限矩阵和审计事件同步更新；
- 用户文档、开发文档和运维文档同步更新；
- 性能基线无不可解释的明显退化；
- 升级和回滚路径经过验证；
- 没有阻断下一版本语义的遗留 P0/P1 问题。

### 10.2 不允许跨版本透支的事项

- V1.2 不能以“以后再补恢复”为理由开放不可撤销的脚本执行路径。
- V1.3 不能在缺少预览和真实字节码验证的情况下增加增强位置。
- V1.4 不能通过恢复最初 class bytes 的方式宣称支持其他 Agent 共存。
- V1.5 不能只凭人工 Demo 宣称兼容，必须进入自动化矩阵。
- V1.6 不能为 MCP 或 AI 建立绕过 Platform API、权限和审计的旁路。
- V1.7 不接受新的主要功能，只处理封版质量和必要的契约修正。

### 10.3 V1.X 封版后的维护范围

V1.7 LTS 发布后，V1.X 只接受：

- 缺陷修复；
- 安全修复；
- 性能优化；
- 新 JDK 小版本和框架兼容性维护；
- API V1 向后兼容维护；
- 文档和诊断能力改进。

录制回放、数据集、分布式实验编排以及其他新的产品领域进入 V2.0，不再扩大 V1.X 的方法增强边界。

## 11. 推荐执行顺序

各版本不绑定固定自然日期，以验收结果作为进入下一阶段的条件。推荐推进方式如下：

1. V1.1 先建立字节码事实来源，后续所有增强和恢复都以此验证。
2. V1.2 在可观察、可诊断和可恢复的基础上开放完整脚本权限。
3. V1.3 复用统一脚本和预览能力扩展关键增强位置。
4. V1.4 在增强位置稳定后定义组合、冲突、事务和精确卸载语义。
5. V1.5 使用已经稳定的增强语义完成复杂 JVM 场景兼容。
6. V1.6 在底层契约稳定后冻结公开 API，并构建 AI、CLI 和 MCP 接口。
7. V1.7 停止增加功能，完成性能、长稳、升级和 LTS 封版。

这一路径完成后，Kairo 的方法增强能力即达到 V1.X 产品边界内的最终形态。
